## 1. 배경 — 이 문제가 대두된 이유

v1.14.0에서는 사용자의 승인 대기 시간을 45초 단위의 슬라이스(분할 주기)로 나누어 처리하도록 개선했습니다. 클라이언트의 60초 타임아웃 제한으로 인해 도구 호출이 비정상 종료되며 대화가 끊어지던 문제는 해결되었으나, 그 결과 **도구 호출 횟수가 크게 증가했습니다.** 사용자가 5분 동안 검토하면 11회, 15분 동안 검토하면 20회의 분할 호출이 발생합니다.

도구 호출 빈도가 늘어나면서 기존부터 제기되던 근본적인 의문이 더욱 중요해졌습니다. 바로 **"매 응답마다 전체 작업(태스크) 목록을 다시 전송하는 것이 바람직한가?"**라는 점입니다. 현재 `handlers.py` 내 37곳에서 `tasks=plan.tasks_brief()`를 호출하고 있어, 사실상 거의 모든 응답이 전체 계획 정보를 중복 전송하고 있습니다.

이러한 설계 자체에는 타당한 이유가 있습니다. 이 프로젝트의 핵심 전제가 *"소형/경량 모델에 대화 기억(컨텍스트 유지)을 요구하지 않는다"*는 것이며, 매 응답마다 전달되는 `next_action`과 전체 진행 상태가 바로 이 전제를 뒷받침하기 때문입니다. 다만 문제는 이러한 상태 재전송에 소모되는 토큰 비용이 구체적으로 측정된 적이 없다는 점입니다.

## 2. 측정 방법 (재현 가능한 기준)

실제 프로덕션 코드(`responses.build`, `models.Task.brief`, `schemas.build_tool_definitions`)를 바탕으로
페이로드를 생성하고 UTF-8 바이트 크기를 직접 측정했습니다.

- **토큰 환산 기준: `bytes // 3`.** BPE(Byte Pair Encoding) 기준 한국어는 대략 1.2~1.7글자당 1토큰,
  JSON 문법 구조는 약 4글자당 1토큰 수준입니다. 둘이 혼합된 페이로드 특성을 감안해 중간값으로
  추산한 결과입니다. 따라서 **약 ±30%의 오차 범위를 고려해야 합니다.**
  보다 정확한 수치가 필요할 경우 실제 배포 대상 모델의 토크나이저로 재측정해야 합니다.
- 시나리오 기준: 태스크 5개, 한국어 제목, `min_result_log` 검증 규칙을 충족하는 길이의
  작업 결과 증빙 로그(80~110자).
- "청구 토큰(Billed Tokens)"은 프롬프트 캐싱이 **적용되지 않는 환경**을 가정하여, 매 턴마다 누적된
  전체 대화 이력을 다시 읽는 비용의 총합(누적합의 합계)입니다. 캐싱 지원 여부에 따른 영향은 §5에서 다룹니다.

본격적인 작업에 착수하기도 전에, **매 요청마다** 기본적으로 다음과 같은 토큰이 소모됩니다.

| 항목 | 토큰 |
|---|---:|
| `plan_and_think` 스키마 | 1,367 |
| `update_task_progress` 스키마 | 787 |
| `request_user_approval` 스키마 | 732 |
| `get_current_plan` 스키마 | 186 |
| **`tools/list` 합계** | **3,072** |
| `agents.md` 시스템 프롬프트 | 1,808 |
| **고정 오버헤드** | **4,880** |

이는 단순한 낭비가 아니라 **의도된 설계적 투자**입니다. Phase 1 청사진에서 "소형/경량 모델의
안정적인 도구 활용을 위해 모든 매개변수에 구체적인 예시(Example)를 제공한다"는 원칙을 세웠으며,
실제 테스트 매트릭스(E16·E17)에서도 이처럼 상세한 설명이 클라이언트 측의 형식 오류를 효과적으로
방지했음을 확인했습니다.

그럼에도 불구하고 직면한 한계는 명확합니다:

- **4k 컨텍스트 모델에서는 하네스 구동 자체가 어렵습니다.** 도구 스키마 정의만으로 전체 컨텍스트 창의 75%를 차지합니다.
- **8k 모델에서도 실제 작업을 위해 활용 가능한 여유 공간이 3,300 토큰에 불과합니다.**

사내 LLM의 실제 컨텍스트 창 용량을 사전에 파악하지 못하면 이후의 모든 최적화 분석은 무의미해집니다.
**이 점이 §8에서 가장 먼저 확인해야 할 필수 항목입니다.**

## 4. 발견 2 — 상태 재전송 누적으로 인한 토큰 낭비

### 단일 응답의 토큰 구성

```
전체 응답 페이로드        520 tok
에코 제거 시              90 tok
─────────────────────────────
에코(상태 재전송) 자체   430 tok   ← 단일 응답의 82% 차지
```

### 실행 단계 6회 호출(IN_PROGRESS 1회 + DONE 5회) 누적치

```
누적 에코 토큰        2,782 tok
최신 사본 1개 분량       520 tok
─────────────────────────────
과거 상태의 중복 데이터 2,262 tok   ← 전체 에코 예산의 81%
```

마지막 턴 시점의 컨텍스트 창에는 태스크 목록 사본이 **총 6개** 존재하게 되며, 그중 **5개는 이미 지나간 과거 상태**입니다.

### 작업 결과 로그가 미치는 영향

`Task.brief()`는 작업 결과(`result_log`)를 임의로 자르지 않습니다. D18(v1.13.1) 당시 **의도적으로**
길이 제한(캡)을 해제했기 때문입니다. 승인 화면이 동일한 딕셔너리 데이터를 기반으로 구성되는데,
증빙 결과가 말줄임표(`...`)로 생략되면 사람이 직접 검증할 수 없다는 판단이었습니다. 그 방향 자체는
타당했으나, 동일한 딕셔너리가 매 턴마다 모델의 입력 컨텍스트로도 그대로 재전송된다는 점이 문제입니다.

| 태스크 수 | 증빙 로그 길이 | 1회 전송 시 에코 | 전체 누적 에코 |
|---:|---:|---:|---:|
| 5 | 40자 | 562 | 3,372 |
| 5 | 120자 | 962 | 5,772 |
| 5 | 400자 | 2,362 | 14,172 |
| 8 | 120자 | 1,484 | 13,356 |
| 12 | 120자 | 2,183 | 28,379 |
| 12 | 400자 | 5,543 | **72,059** |

도구 호출 횟수가 태스크 수와 거의 비례하므로, **태스크 수에 대해서는 O(n²), 결과 로그 길이에 대해서는 선형(O(n))**으로 증가합니다.
특히 `max_tasks` 기본값이 12라는 점을 감안하면, 위 표의 마지막 행은 기본 구성에서도 충분히 도달할 수 있는 수치입니다.

`models.py:172`의 코드 주석에서도 이미 이러한 상황을 다음과 같이 예견하고 있었습니다:

> *"작업 결과 기록이 컨텍스트 한도를 위협하게 되면, 데이터를 읽는(조회) 시점이 아니라 **저장하는(쓰기) 시점**에
> 길이 제한을 걸어야 한다(`min_result_log`와 함께 최댓값 설정). 조회 시점에 임의로 잘라내면
> 데이터 저장소 원본과 암묵적인 불일치가 발생하기 때문이다."*

### 분할 대기 슬라이스 비용

v1.14.0 도입으로 추가된 토큰 비용 구조입니다.

```
APPROVAL_PENDING 단일 응답     240 tok   (태스크 목록 미포함 — 의도된 설계)
그중 next_action_hint         128 tok   ← 글자 하나 틀리지 않고 매번 반복 전송
5분간 검토 대기 시 (11슬라이스) 2,640 tok   = 전체 작업 토큰의 약 38%
15분간 검토 대기 시 (20슬라이스) 4,800 tok
```

승인 대기 슬라이스 응답에 태스크 목록을 싣지 않은 것은 훌륭한 설계입니다(승인 완료로 오인될 여지를 차단).
다만 128토큰에 달하는 동일한 안내 문구를 11~20회씩 그대로 반복하는 것은 명백한 낭비입니다.

## 5. 발견 3 — 컨텍스트 창 포화 문제

작업 완료 시점의 컨텍스트 창 점유량 (고정 오버헤드 4,880 토큰 및 승인 대기 슬라이스 11회 포함):

| 태스크 수 | 증빙 로그 길이 | 피크 토큰 | 4k | 8k | 16k | 32k |
|---:|---:|---:|:-:|:-:|:-:|:-:|
| 5 | 40자 | 10,802 | ✗ | ✗ | ○ | ○ |
| 5 | 120자 | 13,202 | ✗ | ✗ | ○ | ○ |
| 5 | 400자 | 21,602 | ✗ | ✗ | ✗ | ○ |
| 8 | 120자 | 20,285 | ✗ | ✗ | ✗ | ○ |
| 12 | 120자 | 34,314 | ✗ | ✗ | ✗ | ✗ |
| 12 | 400자 | 77,994 | ✗ | ✗ | ✗ | ✗ |

**컨텍스트 창 포화로 인한 장애가 외부로 드러나지 않고 '조용히 실패(silent failure)'한다는 점이 가장 치명적인 위험입니다.** 컨텍스트 창 한도를 초과하면 호스트 애플리케이션(AnythingLLM 등)은 대개 가장 오래된 이전 메시지부터 순차적으로 잘라냅니다. 그 결과 유실되는 대상은 다름 아닌 **시스템 프롬프트, 원래의 목표, 사용자가 승인한 계획**입니다. 즉, 제어 하네스가 존재하는 근본적인 이유가 통째로 사라지는 것입니다. 컨텍스트 창에는 오직 최근의 도구 실행 결과만 남게 되며, 모델은 준수해야 할 행동 규칙도 없이 상태 데이터 파편만 쥔 채 작업을 비정상적으로 계속하게 됩니다. 서버 입장에서는 이러한 컨텍스트 유실을 감지할 방법이 전혀 없습니다.

이는 앞서 겪었던 D1 결함과 본질적으로 동일한 유형의 실패입니다. D1 결함은 만료된 과거 승인으로 후속 작업이 인가되는 위험을 **TTL(유효 시간)**로 방어했으나, **대화 컨텍스트 창에는 이러한 TTL 개념이 존재하지 않습니다.**

### 프롬프트 캐싱 지원 여부에 따른 영향

| 구분 | 누적 추가(Append) 토큰 | 청구 토큰(Billed Tokens) |
|---|---:|---:|
| 현재 방식 (전체 에코 유지) | 2,782 | 9,127 |
| 작업 결과 증빙 전면 제외 | 2,059 | 7,424 (−18%) |

- **vLLM, SGLang 등 자동 프리픽스 캐싱(Automatic Prefix Caching)이 지원되는 환경**: 이전 대화 이력을 다시 읽는 비용이 거의 들지 않으므로 '청구 토큰' 항목은 큰 의미가 없고 매 턴 새로 추가되는 '누적 추가' 토큰만이 실질적인 비용이 됩니다.
- **캐싱이 지원되지 않는 환경**: 매 턴마다 누적된 전체 이력을 재전송하므로 '청구 토큰' 비용이 고스란히 발생합니다.
- **어느 환경이든 컨텍스트 창 포화 문제(위 표)는 동일하게 발생합니다.** 캐싱은 연산 비용과 지연 시간을 줄여줄 뿐, 물리적인 컨텍스트 창 용량을 늘려주지는 못하기 때문입니다.

## 6. 발견 4 — 컨텍스트 중간 정보 유실 (Lost in the Middle)

대규모 언어 모델(LLM)은 입력 컨텍스트의 **처음과 끝**에 배치된 정보는 정확히 인지하지만, **중간** 부분에 위치한 정보는 쉽게 놓치는 경향이 있습니다 (Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*, arXiv 2307.03172). 이러한 현상은 모델 크기가 작을수록 한층 뚜렷하게 나타나며, 본 프로젝트가 주 타깃으로 삼는 모델군이 바로 이와 같은 소형/경량 모델입니다.

### 현재 설계의 강점 (반드시 유지해야 하는 요소)

- **`next_action` 지시가 항상 컨텍스트의 최하단(맨 끝)에 위치합니다.** 모델의 주목도(Attention)가 가장 집중되는 위치에 가장 핵심적인 실행 지시를 배치한 것입니다. 이는 단순한 우연이 아니라 "매 응답마다 다음 수행할 단 하나의 행동을 명시한다"는 설계 원칙의 성과입니다.
- 시스템 프롬프트가 대화의 맨 앞(최상단)에 위치하여 두 번째로 높은 주목도를 유지합니다.
- 최신 진행 상태 역시 최하단에 배치됩니다. 과거의 낡은 사본들은 자연스럽게 중간 영역으로 밀려나 상대적으로 주목을 덜 받게 됩니다.

### 잠재적인 위험 요소

**과거의 낡은 사본에는 단순한 이전 데이터뿐 아니라, 모델이 실행 가능한 형태로 작성된 과거의 지시문까지 고스란히 남아 있습니다.**
`state_machine.py:288`에서 힌트에 구체적인 ID 값을 직접 하드코딩하기 때문입니다:

```python
f"Call update_task_progress with task_id={task.task_id} and status='IN_PROGRESS'."
```

예컨대 태스크 5를 수행하는 시점에도 대화 이력에는 *task_id 1, 2, 3, 4의 실행을 지시하는 문장 4개*가 여전히 살아 있습니다. 이는 단순한 데이터가 아니라 명확한 **실행 명령문**이며, 현재 시점에서는 모두 유효하지 않은 지시입니다. 정보의 부재보다 상충되는 정보(모순)가 훨씬 위험합니다. 정보가 없으면 모델은 사용자에게 다시 질문하지만, 서로 다른 여러 개의 지시를 목격한 모델은 그중 하나를 임의로 선택해 오작동하기 때문입니다.

### ⚠ 주의: 직관과 다른 점 — 작업 결과 증빙을 전면 제거하면 오히려 성능이 저하됩니다

태스크 N은 이전 태스크(N−1)의 산출물을 입력값으로 참조해야 하는 경우가 많습니다(예: "추출된 매출 집계표"를 바탕으로 다음 단계에서 "증감률 계산"을 수행). 해당 산출물이 처음 보고된 곳은 태스크 N−1의 DONE 응답이며, 이후 턴이 거듭될수록 이 정보는 컨텍스트의 **중간 영역으로 밀려나게 됩니다.**

현재 시스템에서는 에코(상태 재전송) 기능이 매 턴마다 이를 최신 컨텍스트 하단으로 다시 끌어올려 주고 있습니다. 즉, **상태 재전송 메커니즘이 '중간 유실(Lost in the middle)' 현상을 자연스럽게 방어하는 완충 역할을 함께 수행하고 있는 것입니다.**

따라서 토큰을 아끼겠다고 '결과 증빙 로그를 전면 제외'하는 것은 득보다 실이 큰 선택입니다:

| 방식 | 청구 토큰 | 절감률 | 중간 유실(Lost-in-the-middle) 방어 |
|---|---:|---:|---|
| 전체 포함 (현재 방식) | 9,127 | — | 안정적으로 방어됨 |
| **직전 태스크 증빙만 유지** | **8,143** | **−10%** | **방어력 유지** |
| 결과 증빙 전면 제외 | 7,424 | −18% | **심각한 정보 유실 발생** |

불과 8%의 추가 토큰 절감을 얻기 위해 태스크 간의 실질적인 데이터 의존성을 깨뜨리는 것은 명백한 손해입니다. **§7의 제안 2는 바로 이러한 판단에 근거하고 있습니다.**

## 7. 개선 제안

우선순위가 높은 순서대로 정리했으며, 각 방안은 독립적으로 적용할 수 있습니다.

### 제안 1 — `result_log`를 저장하는(쓰는) 시점에 길이 제한 적용 (효과 높음 / 위험 낮음)

`min_result_log` 검증 규칙 옆에 `max_result_log`(예: 300자)를 두고, `update_task_progress` 도구가 입력을 받는 시점에 길이를 제한(절삭)합니다. 이는 `models.py:172` 주석이 권장하는 바로 그 방식입니다.

- **장점**: 사람이 검증하는 화면과 모델이 참조하는 데이터가 계속 일치하므로 D18 결함 대응으로 확보한 보장 원칙을 깨뜨리지 않습니다. 또한 §4 표에 나타난 400자 이상의 극단적인 토큰 폭증 행이 원천 차단됩니다.
- **단점**: 결과 내용이 일부 잘려 저장되었다는 사실을 모델에게 명확히 피드백해야 합니다(그렇지 않으면 후속 재작업 시 모델이 자신의 이전 산출물이 축약된 사실을 인지하지 못합니다). 절삭 표시와 함께 "상세 전체 내용은 저장소 파일에 보관되어 있다"는 안내를 추가하는 방안을 권장합니다.
- **주의 사항**: 단순히 길이를 자르는 대신 입력을 **거부(Reject)**하는 대안도 고려할 수 있습니다("내용이 너무 길어 수용할 수 없으니 요약하여 다시 제출하라"). 그러나 경량 모델에게 실패 후 재작성을 요구하면 성공률이 현저히 떨어지므로, 서버에서 안전하게 최대 길이로 잘라 처리하는 편이 실용적입니다(실제 환경 검증 필요).

### 제안 2 — 모델 전달용 에코에서 오래된 작업 증빙만 선별 제외 (효과 중간 / 위험 낮음)

`Task.brief()` 메서드를 호출 주체(용도)에 따라 분리합니다:

- `brief()` — 사람이 확인하는 승인 웹 페이지용. **현재 동작을 그대로 유지**하며 전체 작업 증빙을 포함합니다.
- `brief_for_model()` — 모델에게 전달되는 에코용. **직전에 완료된 태스크의 `result_log`만** 유지하고, 그보다 앞선 이전 태스크들의 상세 증빙은 제외합니다. 단, 사용자로부터 재작업 요청을 받은 태스크의 `previous_result_log`는 반드시 유지해야 합니다(`REWORK_NOT_DONE` 방어 가드가 이 필드를 검증하기 때문).

§6에서 분석한 바와 같이, 증빙을 전면 배제해서는 안 되며 **직전 태스크의 산출물은 반드시 보존**해야 합니다.

- **기대 효과**: 청구 토큰 약 10% 절감 (증빙 내용이 길수록 절감 효과가 더욱 극대화됨).
- **잠재 위험**: `handlers.py` 내에서 `tasks_brief()`가 웹 UI로 전달되는 경로와 모델 API 응답으로 전달되는 경로를 철저히 분리해야 합니다. 이를 잘못 혼용할 경우 D18 회귀 버그가 발생할 수 있습니다. 특히 `_wait_for_human` → `open_request` 흐름이 웹 페이지 전용 경로인지 반드시 확인해야 합니다.

### 제안 3 — 힌트 문구에서 하드코딩된 `task_id` 값 제거 (효과 낮음 / 안정성 높음)

`next_action_hint` 안내 문구에서 `task_id=3`과 같은 구체적인 리터럴 값을 제외하고, 이미 독립적으로 제공되고 있는 `next_task` 필드에만 해당 ID를 명시합니다. 힌트 문구는 "`next_task` 필드에 명시된 태스크를 수행하라"는 범용 안내로 전환합니다.

- **기대 효과**: 직접적인 토큰 절감 효과는 미미하지만, **과거 대화 이력의 낡은 사본들이 실행 가능한 명령문 형태에서 단순 참조용 데이터로 격하**됩니다. 이로써 §6에서 지적한 과거 명령 오독 위험을 근본적으로 제거할 수 있습니다.
- **잠재 위험**: 간접 참조 방식은 경량 모델에게 이해 난이도가 더 높을 수 있습니다. 현재의 직설적인 힌트가 안정적으로 작동했던 이유가 구체적인 값 명시에 있었을 수 있습니다. **따라서 본 제안은 §8에 기술된 A/B 테스트 검증을 거치기 전에는 섣불리 적용해서는 안 됩니다.** 현재의 힌트 문구는 D14·D19 등 과거 결함들을 해결하는 과정에서 정교하게 다듬어진 핵심 요소입니다.

### 제안 4 — 반복되는 대기 슬라이스의 힌트 문구 압축 (효과 중간 / 위험 낮음)

사용자 승인 대기 중 2회차 이후 발생하는 `APPROVAL_PENDING` 응답에 대해서는 축약된 짧은 힌트를 전송합니다(모델은 이미 1회차 응답에서 전체 안내 문구를 숙지한 상태이기 때문입니다).

```
1회차 응답: 전체 상세 힌트 제공 (약 128 토큰)
2회차 이후: "Not decided. Call request_user_approval ASK_USER again now. No text." (약 20 토큰)
```

- **기대 효과**: 11회 슬라이스 기준 약 1,000 토큰, 20회 슬라이스 기준 약 2,000 토큰을 절감할 수 있습니다.
- **잠재 위험**: 모델이 짧아진 힌트를 간과하고 승인 대기 루프를 이탈할 우려가 있습니다. 다만 이탈하더라도 서버 측의 APPROVAL_PENDING 가드(D20)가 승인 없이 진행되는 상태 변경을 엄격히 차단하므로, 치명적인 오작동 대신 불필요한 재시도 토큰만 소모되는 선에서 통제됩니다.
- **대안 방안**: 슬라이스 호출 주기(`call_budget`)를 클라이언트 60초 타임아웃 제한에 가깝게 늘려 전체 슬라이스 발생 횟수 자체를 줄이는 방법도 가능합니다. 단, 사전에 실측된 클라이언트 허용 한계치(`client_caps.json`)를 초과해서는 안 됩니다.

### 제안 5 — 도구 스키마 정의 경량화 (효과 높음 / 위험 높음)

MCP 서버 자체는 클라이언트의 실제 컨텍스트 사용량을 직접 조회할 수 없지만, **서버가 클라이언트에 전달한 누적 응답 바이트 크기는 정확히 측정할 수 있습니다.** 플랜별 누적 전송 바이트를 `audit.jsonl`에 상시 기록하고 사전 설정된 임계치를 초과할 경우 경고를 남기면, §5에서 지적한 '조용한 컨텍스트 유실'을 사전에 감지하고 추적할 수 있습니다. 또한 복구 도구로 `get_current_plan`이 이미 마련되어 있으므로, 한도 초과 시 "컨텍스트 한도가 임박했으니 새 세션을 열고 `get_current_plan`으로 상태를 동기화하라"는 안내를 안전하게 전달할 수 있습니다.

## 8. 구현에 착수하기 전 반드시 실측해야 할 항목

**본 문서에 수록된 어떠한 최적화 제안도 실제 환경에서의 실측 데이터 없이 섣불리 적용해서는 안 됩니다.** v1.14.0에서 수정되었던 결함이 정확히 이러한 오류에서 비롯되었습니다. 공식 문서에 적힌 기본값(`resetTimeoutOnProgress`)을 사전에 직접 검증하지 않고 맹신한 채 안전장치를 구축했으나, 실제 동작 기본값이 정반대였던 사례가 있었습니다(D21).

단계별 필수 확인 사항:

1. **사내 LLM 인프라의 실제 컨텍스트 창 크기.** 모델이 지원하는 창 크기가 4k인지 32k인지에 따라 §5 분석 결과와 대응 전략이 완전히 달라집니다. 이 기준값이 확인되지 않으면 다른 모든 분석은 무의미합니다.
2. **컨텍스트 한도 초과 시 AnythingLLM의 메시지 절단 정책.** 앞부분의 오래된 메시지를 순차 삭제하는지, 중간 요약을 수행하는지, 에러를 반환하며 중단되는지 확인해야 합니다. 앞부분을 잘라내는 방식이라면 §5에서 지적한 '조용한 실패'가 실제로 발생하게 됩니다.
3. **추론 엔진의 프리픽스 캐싱(Prefix Caching) 지원 여부.** 배포된 추론 서버가 vLLM이나 SGLang 계열인지 확인해야 합니다. §5의 '청구 토큰' 항목이 실질적인 비용으로 청구되는지 여부가 여기서 결정됩니다.
4. **실제 배포 모델의 토크나이저를 통한 정확한 토큰 수 재측정.** 본 문서에서 사용한 `bytes // 3` 공식은 휴리스틱 추정치이므로, 실제 모델의 어휘집(Vocabulary)을 바탕으로 정밀 검증이 필요합니다.
5. **시스템 장애가 어느 지점에서 먼저 발생하는지 실제 관찰.** 컨텍스트 창 포화로 인한 기억 유실이 먼저 발생하는지, 아니면 과거의 낡은 지시문을 오독하여 오작동하는지가 관건입니다. 두 문제의 해결책이 상이하므로, 실제 장애 양상을 직접 확인하지 않고 수정하는 것은 또 다른 억측 기반 최적화에 불과합니다.

가장 적은 리소스로 안전하게 실측할 수 있는 방법은 **제안 6(컨텍스트 포화 감지 로그)을 먼저 구현하는 것**입니다. 코드 변경 범위가 매우 작으면서도, 향후 모든 최적화 의사결정의 명확한 데이터 근거를 확보할 수 있습니다.

## 9. 절대 훼손해서는 안 되는 핵심 보장 원칙

성급한 최적화 과정에서 자칫 무너지기 쉬우며, 수많은 결함 대응과 디버깅을 거쳐 값비싸게 확립된 핵심 불변 조건들입니다. 어떤 제안을 적용하더라도 다음 보장들이 깨지지 않는지 반드시 교차 검증해야 합니다.

|---|---|---|

## 부록 — 측정 재현 방법

본 문서에 제시된 모든 측정 수치는 저장소 내 실제 프로덕션 코드를 실행하여 산출한 결과입니다. 별도의 재현 스크립트를 저장소에 상시 커밋하지 않은 이유는, 일회성 분석 도구로 인한 불필요한 코드 유지보수 부채를 방지하기 위함입니다. 동일한 측정이 필요할 경우 아래 코드를 활용하여 언제든 재현할 수 있습니다:

**직렬화 방식이 두 가지로 나뉜다는 점에 유의해야 합니다.** 도구 정의 스키마와 실행 응답 페이로드는 서로 다른 방식으로 인코딩되므로, 동일한 방식으로 측정하면 본 문서의 표와 다른 수치가 나올 수 있습니다.

- **응답 페이로드**: `protocol.py`에서 `json.dumps(payload, ensure_ascii=False, indent=2)`로 직렬화하여 모델에게 전달합니다. JSON 들여쓰기 공백이 실제로 전송되므로 **`indent=2` 옵션을 적용하여 측정해야 합니다.**
- **도구 정의 스키마**: 클라이언트가 `tools/list` 결과를 수신한 뒤 자체 포맷으로 재직렬화하여 프롬프트에 포함합니다. 일반적으로 불필요한 공백이 제거된 압축(Compact) 형태로 처리되므로 **`indent` 없이 한 줄로 직렬화하여 측정하는 것이 실제 환경에 부합합니다.** (`indent=2`로 측정하면 3,462 토큰이 산출되며, 이것이 본 문서 표의 3,072 토큰과 차이가 발생하는 이유입니다.)

```python
from planning.models import Plan, Task, PlanStatus, TaskStatus
from planning.responses import build
from planning.schemas import build_tool_definitions
import json

compact = lambda p: len(json.dumps(p, ensure_ascii=False).encode()) // 3
wire    = lambda p: len(json.dumps(p, ensure_ascii=False, indent=2).encode()) // 3

# 고정 오버헤드 — 클라이언트가 재직렬화하므로 압축 기준
print(sum(compact(t) for t in build_tool_definitions(auto_advance=True)))   # 3072

# 에코 1회 — 서버가 전송하는 실제 형태 기준
p = Plan("p", "목표", plan_status=PlanStatus.IN_EXECUTION.value,
         tasks=[Task(1, "제목", TaskStatus.DONE.value, result_log="증거"*30)])
print(wire(build(p, tasks=p.tasks_brief(), progress=p.progress())))
```

"청구 토큰(Billed Tokens)"은 프롬프트 캐싱이 지원되지 않는 환경을 전제로 한 누적합(Prefix sum)의 총합입니다:

```python
def billed(seq):
    ctx = total = 0
    for x in seq:
        ctx += x        # 도구 실행 결과가 대화 이력에 추가됨
        total += ctx    # 다음 도구 호출 시 전체 누적 이력을 다시 읽음
    return total
```
