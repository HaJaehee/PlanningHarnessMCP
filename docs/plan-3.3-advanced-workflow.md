## 0. 한 줄 요약

`ADVANCED_WORKFLOW_PLANNING=1`이면 에이전트가 최종 계획과 함께 **Mermaid flowchart**를 전송하고, 서버는 이를
**순수 Python lint 가드**로 자동 보정하거나 반려한 후 **정규화된 Mermaid 텍스트**만 승인 페이지로 전달합니다. 페이지는
**함께 번들링된 mermaid.js**로 다이어그램을 시각화하고, 사용자는 노드를 클릭하여 검토 의견을 작성하며, 의견이 입력되면 `승인` 버튼이
`수정 요청(워크플로우)`로 전환됩니다. `0`(기본값)이면 도구 텍스트·페이지·지문·응답이 **3.2와 바이트 단위로 동일합니다.**

## 1. 의존성 원칙의 예외 — 무엇을 허용하고 무엇은 그대로인가

현재 원칙 (wiki README "Ground rules" 1): *Zero third-party dependencies. Standard library only.*

### 1.1 예외 문안 (wiki README, 01-overview, 배포 매뉴얼에 들어갈 내용)

> 1. **서버 런타임(Python)은 모든 모드에서 표준 라이브러리만 사용합니다.** `pip install`은 어떤 설정에서도 필요하지 않습니다.
> 1a. **예외: `ADVANCED_WORKFLOW_PLANNING=1`일 때 승인 페이지는 브라우저 단에서 mermaid.js(MIT)를 사용합니다.**
>     - 에셋 파일은 `vendor/mermaid/`에 **버전 및 SHA-256 해시를 고정**하여 함께 패키징하며, CDN이나 외부 네트워크 통신은 일절 사용하지 않습니다.
>     - 플래그가 `0`이면 서버는 해당 파일을 읽거나 브라우저로 전송하지 않습니다. 파일이 없어도 서버는 정상 기동합니다.
>     - 플래그가 `1`이지만 파일이 누락되었거나 해시가 불일치하면 **명확한 경고와 함께 단계적 기능 축소(Graceful Degradation)** 방식으로 동작합니다: 페이지는 다이어그램 대신 정규화된
>       Mermaid 원문 텍스트를 표시하며, 의견 작성 및 수정 요청 기능은 정상 작동합니다. 어떠한 경우에도 승인 게이트가 우회되거나 해제되지 않습니다.
>     - 다른 서드파티 라이브러리나 에셋에는 이 예외가 적용되지 않습니다. 새로운 예외가 필요한 경우 본 목록에 별도로 명시해야 합니다.

### 1.2 `requirements.txt`에 대하여 — 권장: 만들지 않고 `vendor/manifest.json`으로 대신함

Mermaid는 **JavaScript 라이브러리**이며, 순수 Python 패키지만으로는 오프라인 환경에서 Mermaid를 파싱·렌더링할 수 없습니다.
PyPI의 `mermaid-py` 등은 외부 웹 서비스(mermaid.ink)를 호출하거나 Node/Chromium 런타임(`mermaid-cli`)을 요구하므로
폐쇄망 환경에서는 둘 다 적용할 수 없습니다. 따라서 본 기능을 활성화하더라도 **Python 런타임 단에 추가로 설치할 패키지는 없습니다.**

`requirements.txt` 파일을 생성하면 파일 내용이 비어 있더라도 보안 검토자와 시스템 운영자에게 "pip 패키지 설치가 필요하다"는
불필요한 혼선을 줄 수 있습니다. 대신 실제 에셋 의존성을 명확하게 명시하는 전용 매니페스트 파일을 둡니다.

```
vendor/
  manifest.json          # 번들 서드파티 에셋 목록: 이름, 버전, 원본 URL, SHA-256, 라이선스, 사용 설정
  mermaid/
    mermaid.min.js       # 버전 고정 (구현 시 11.x 안정판 하나로 고정)
    LICENSE              # MIT (번들에 포함된 DOMPurify·d3 등의 고지 포함)
tools/fetch_vendor.py    # 빌드 PC 전용: manifest의 URL에서 다운로드 후 SHA-256 대조 및 검증하여 저장
```

```json
{ "mermaid": { "version": "11.x.y", "file": "vendor/mermaid/mermaid.min.js",
               "source": "https://cdn.jsdelivr.net/npm/mermaid@11.x.y/dist/mermaid.min.js",
               "sha256": "…", "license": "MIT", "used_when": "ADVANCED_WORKFLOW_PLANNING=1" } }
```

관례상 `requirements.txt`가 꼭 있어야 한다면(사내 스캐너 등) **주석만 있는 파일**로 둡니다:
`# Runtime: none (Python standard library only). Browser asset: see vendor/manifest.json.`
→ **§9 결정 1.**

### 1.3 반입·검증 도구의 변경

| 도구 | 변경 |
|---|---|
| `tools/fetch_vendor.py` (신규) | 빌드 PC 전용 실행. 해시 불일치 시 저장하지 않고 실패 처리 |
| `tools/make_package.py` | 허용 목록에 `vendor/**` 추가, `MANIFEST.txt`에 SHA-256 기록. `--no-vendor` 옵션으로 3.2 버전과 동일한 경량 크기(~110 KB) 패키지도 빌드 지원 (mermaid 포함 시 ~3 MB) |
| `tools/verify_install.py` | 표준 라이브러리 전용 import 검사는 기존 유지. `vendor/manifest.json`이 존재할 경우 각 에셋 파일의 해시를 검증하여 불일치 시 NO-GO 처리, 파일 누락 시 "플래그 1에서 저하 모드로 동작" 경고 출력 |
| 보안 검토 사실 (10-deployment) | "HTML 1페이지 + JSON 3개" → "+ 고정 단일 경로 1개(`/vendor/mermaid.js`, 플래그 1 활성화 시에만 제공, 메모리 상주 서빙, 파일시스템 임의 조회 없음)" |

## 2. 설정

| 변수 | 값 | 기본 | 의미 |
|---|---|---|---|
| `ADVANCED_WORKFLOW_PLANNING` | `1` / `0` (`true`/`false`도 허용, `_env_bool`) | `0` | 기능 전체 on/off |
| `PLANNING_MCP_WORKFLOW_MAX_NODES` | 정수 | `30` | 노드 수가 이보다 크면 lint 검사에서 반려 (페이지 가독성 및 모델 컨텍스트 토큰 절약) |
| `PLANNING_MCP_WORKFLOW_RETRIES` | 정수 | `2` | lint 검사 반려 후 재전송 허용 횟수. 초과 시 서버가 태스크 순서 기반 선형 다이어그램으로 자동 대체 생성 (§4.4) |

변수명은 요청에 따라 `ADVANCED_WORKFLOW_PLANNING`을 기본으로 사용합니다. 다른 설정 항목과의 일관성을 위해
`PLANNING_MCP_` 접두사를 갖는 `PLANNING_MCP_ADVANCED_WORKFLOW`도 별칭(Alias)으로 지원합니다(§9 결정 2). `Config.advanced_workflow` 및
`wiki/data/config.json`에 추가합니다.

## 3. 도구 계약 (모델이 보는 것)

### 3.1 `plan_and_think`에 필드 하나: `workflow` (string)

플래그가 `1`일 때만 스키마에 노출됩니다 (D25: 실행 중인 서버의 실제 기능만 노출). `0`인 상태에서 전달되면 해당 필드를 무시하고
안내 문구(note)를 첨부합니다 (`PLANNING_MCP_ALTERNATIVES=off`와 동일한 처리 방식).

도구 설명에 추가되는 규칙 (한 번만, 짧게 — 메모리 "concise text"):

> With the final task_list, send `workflow`: a Mermaid flowchart of the plan. One node per task with id T1..Tn in
> task order; a decision is D1{...}; start/end are S and E.

파라미터 설명 (형태 + 예시 하나):

```
flowchart TD
  S([시작]) --> T1["매출 파일 읽기"]
  T1 --> D1{"Q3 데이터가 있나?"}
  D1 -->|예| T2["피벗으로 집계"]
  D1 -->|아니오| E([종료])
  T2 --> T3["5줄 요약"] --> E
```

- `TestToolTextIsLean`에 플래그 `1` 토큰 상한을 별도로 설정합니다 (예상 +120~150 토큰). 플래그 `0` 상한은 기존대로 유지합니다.
- **`agents.md`는 수정하지 않습니다.** 단일 프롬프트를 배포하는 환경에서 플래그가 `0`인 서버에 `workflow` 필드를 명시하면
  스키마에 노출되지 않은 필드를 언급하게 되는 모순이 발생합니다 (Ground rule 7). 관련 안내 규칙은 항상 런타임에 전달되는 도구 설명에만 동적으로 포함합니다.
- 사고 단계(`need_more_thinking=true`)에서 전달된 `workflow`는 `draft_workflow` 필드에 초안과 함께 보관 및 제출됩니다 (`draft_tasks`와 동일).

### 3.2 다이어그램과 태스크 목록의 관계 — 핵심 결정

**태스크 목록이 기준 데이터(Source of Truth)이며, 다이어그램은 이를 시각화한 설명 자료입니다.** 실행 순서, 승인 게이트, 상태 머신 전이는 지금과 똑같이 `task_list` 순서를 따릅니다.

- 노드 `T<n>`은 `n`번째 태스크에 대응합니다. lint 검사기에서 **모든 태스크에 대응하는 노드가 빠짐없이 존재하는지, 범위 밖의 불필요한 번호를 가진 `T` 노드가 없는지** 검증합니다.
- `T<n>` 노드의 라벨은 서버가 **태스크 제목으로 자동 동기화(덮어쓰기)**합니다 (모델이 라벨을 다르게 작성하더라도 일치시킴). 이를 통해 사용자가 다이어그램에서 확인한
  내용과 실제 태스크 목록이 불일치하는 문제를 원천 방지합니다. 모델은 라벨 없이 `T3` 식별자만 지정해도 무방합니다.
- 분기 노드(`D`)는 "조건 충족 여부에 따라 특정 작업을 건너뛸 수 있음"을 사용자에게 시각적으로 안내하기 위한 용도입니다. 서버 내부 상태에 SKIPPED 상태가 없으므로
  건너뛴 태스크는 지금처럼 `DONE` + `result_log`("조건 미충족으로 작업 생략")로 보고합니다. → **§9 결정 3** (SKIPPED 상태 도입은 작업 범위 외로 둘 것을 권장).
- 역방향 엣지(`T4 --> T2`, 재시도 루프)는 문법상 허용하되 페이지에서 점선으로 구분 표시하고 안내 note를 부가합니다. 실제 태스크 실행은 기존 순차 처리 방식을 유지합니다.

### 3.3 지문(fingerprint)

Ground rule 5: 승인 결정은 사용자가 실제로 확인한 정확한 버전의 내용과 결합되어야 합니다. 플래그 `1`에서는 `goal + 태스크 제목 + 정규화된 workflow` 문자열의
해시값을 핑거프린트(지문)로 계산합니다. 플래그 `0`에서는 핑거프린트 계산 로직이 기존 3.2와 완전히 동일하게 유지되므로(회귀 테스트로 고정 검증), 기존 승인 대기열의 항목이
서버 업그레이드로 무효화되지 않습니다.

### 3.4 응답

- 최종 호출 응답의 `input_notes`에 `workflow_notes`(lint 단계에서 자동 보정된 내역)를 포함합니다. 모델이 후속 호출에서 동일한 문법 실수를 반복하지 않도록 피드백을 제공하기 위함입니다.
- 실행 중 도구 응답(`next_task` 등)에는 다이어그램 데이터를 포함하지 않습니다 — 컨텍스트 토큰을 절약하고 실제 작업 실행은 태스크 단위로 이루어지기 때문입니다.
- 채팅 모드(웹 UI 비활성화 시): `display_to_user`에 ` ```mermaid ` 코드 블록 형태로 포함합니다 (클라이언트 채팅창에서 Mermaid 렌더링을 지원하면 다이어그램으로 표시되고,
  미지원 시 마크다운 코드로 출력됨). 채팅 모드에서의 사용자 검토 의견은 기존과 동일하게 전체 계획 수정(REVISE) 흐름을 따릅니다.

## 4. Lint 가드 — `planning/workflow.py` (순수 파이썬, 새 모듈)

`evidence.py`·`choices.py`처럼 **패키지의 다른 모듈을 import하지 않고, 절대 예외를 던지지 않는** 순수 함수 모음입니다.

### 4.1 구조: 관대하게 읽고, 엄격하게 다시 쓴다

```
모델 텍스트 ─► repair(텍스트 수준) ─► parse(부분 문법) ─► check(하네스 규칙) ─► emit(정규형)
                 보정 가능 시 자동 보정 및 note          보정 불가 시 오류 목록(줄 번호 + 원문 + 수정 가이드)
```

**브라우저 UI로 전달되는 데이터는 모델이 생성한 원문 텍스트가 아니라, 서버가 파싱한 AST에서 재생성한 엄격한 정규형(Canonical Form) 텍스트뿐입니다.** 정규형은 모든 텍스트 라벨을 큰따옴표로
감싸고 특수문자를 HTML 엔티티로 이스케이프하며, 화이트리스트 기반 지원 문법만 사용합니다. 따라서 브라우저에서 mermaid.js 파싱 오류가 발생한다면 이는 "모델 출력 결함"이 아니라
"서버 정규형 출력기(emit)의 버그"를 의미하며, 이는 단위 테스트를 통해 사전에 완벽히 방지할 수 있습니다.

지원 부분 문법 (그 밖은 오류):
- 헤더 `flowchart`/`graph` + `TD|TB|LR|RL|BT`
- 노드 모양: `[ ]` `( )` `([ ])` `(( ))` `[[ ]]` `{ }`
- 간선: `-->` `---` `-.->` `==>`, 라벨 `-->|x|` / `-- x -->`, 체인 `A --> B --> C`, `A & B --> C`
- `subgraph id ["제목"]` … `end`
- `%%` 주석 (버림)

### 4.2 자동 보정 (안내 note 첨부 후 정상 통과)

LLM이 Mermaid 문법을 생성할 때 흔히 발생하는 오류 유형입니다. 각 항목별로 테스트 코퍼스를 구성하여 회귀 검증을 수행합니다.

| # | 흔한 실수 | 예 | 보정 처리 |
|---|---|---|---|
| R1 | 마크다운 코드 펜스 포함 전송 | ` ```mermaid … ``` ` | 코드 펜스 제거 |
| R2 | JSON 이스케이프된 줄바꿈 | 한 줄에 `\n`이 글자로 들어 있음 | 실제 줄바꿈 문자로 복원 |
| R3 | 헤더 누락 또는 잘못된 방향 | `A --> B`로 시작, `flowchart TOP` | 기본값 `flowchart TD` 보충 |
| R4 | 따옴표 없는 라벨 내 특수문자 | `A[파일 읽기 (csv)]`, `B{완료?: 예}`, `C[a/b & c]` | 라벨을 `"…"`로 감쌈 |
| R5 | 라벨 내부 큰따옴표 | `A["그가 "OK" 함"]` | `#quot;` 엔티티로 치환 |
| R6 | 예약어 `end`·`graph`·`subgraph`를 노드 ID로 사용 | `end([종료])`, `T3 --> end` | ID를 `E` 등으로 안전하게 변환하고 참조 동기화 |
| R7 | 화살표 직후 `o`/`x` 시작 식별자 결합 | `A-->ok` (원형 간선으로 해석됨), `A---xB` | 화살표 전후 공백 보정 |
| R8 | 비표준 화살표 문법 | `A -> B`, `A => B`, `A —> B`(em dash), `A → B` | 표준 `-->` 화살표로 치환 |
| R9 | 간선 라벨 형식 오류 | `-->|예|>`, `--|예|-->`, `-->|"예" |` | 표준 `-->|"예"|` 형식으로 보정 |
| R10 | 스마트 따옴표 및 전각 괄호 | `A[“시작”]`, `A（시작）` | 표준 ASCII 문자로 치환 |
| R11 | `subgraph` 닫는 태그 누락 | 마지막 subgraph가 안 닫힘 | 말단에 `end` 보충 |
| R12 | 줄 끝 세미콜론, 중복 공백, 탭 | | 불필요한 공백 및 세미콜론 정리 |
| R13 | 동일 ID를 서로 다른 라벨로 중복 정의 | `T1[읽기]` … `T1[불러오기]` | 최초 정의 유지 및 안내 note 첨부 |
| R14 | `T` 노드 라벨이 실제 태스크 제목과 불일치 | | 실제 태스크 제목으로 자동 동기화 및 note 첨부 (§3.2) |
| R15 | 라벨 내부 HTML 태그 / `<br>` | `A[1단계<br>읽기]`, `<b>` | `<br>`은 줄바꿈으로 변환, 기타 HTML 태그 제거 |

### 4.3 보안상 제거 대상 (안내 note 첨부)

`click …`(JS 콜백/외부 링크), `%%{init: …}%%` 설정 지시자, `style`/`classDef`/`class`/`linkStyle`(노드 색상은 서버가 상태에 맞춰 동적 부여),
`:::클래스` 접미사 등은 제거합니다. 프론트엔드 승인 페이지 역시 `securityLevel: 'strict'` 설정으로 렌더링하므로 이중 방어 계층을 이룹니다.

### 4.4 반려 (자동 보정 불가 항목)

| 코드 (`error_code` 아님, `workflow_errors[]` 항목) | 예 |
|---|---|
| `NOT_FLOWCHART` | `sequenceDiagram`, `gantt` |
| `TASK_NODE_MISSING` / `TASK_NODE_UNKNOWN` | T2가 없음 / 태스크가 3개인데 T5가 있음 |
| `BAD_NODE_ID` | `데이터 읽기 --> B` (공백 있는 id) |
| `UNBALANCED` | `A[시작)` 괄호 짝이 안 맞음 |
| `UNREACHABLE` | 시작에서 닿지 않는 태스크 노드 |
| `TOO_LARGE` | 노드 > `WORKFLOW_MAX_NODES` |

반려 시 처리 방식 — 모델이 무한 대기 상태에 빠지지 않도록 보장하는 원칙(D25, "never strand the model"):

1. 최종 호출에 대해 **`ok:false`, `error_code: WORKFLOW_INVALID`**를 반환합니다. 계획 상태는 `DRAFTING`으로 유지되며, 기존 태스크 목록은
   `draft_tasks`에 안전하게 보존되므로 모델이 다시 전송할 필요가 없습니다. 힌트 메시지에는 오류 발생 행(행 번호, 원문, 수정 가이드)과 함께 **현재 태스크 목록을 기반으로 서버가
   자동 생성한 선형 워크플로우 예시**를 제공합니다: "Send workflow again (task_list is kept). Line 4 `데이터 읽기 --> B`: a node id
   cannot contain spaces - use T1["데이터 읽기"]."
2. `PLANNING_MCP_WORKFLOW_RETRIES`(기본값 2) 초과 시 서버가 **태스크 순서에 맞춘 선형 다이어그램을 자체 생성**하여 사용자 승인 단계로
   전환합니다. 페이지에는 "에이전트의 워크플로우를 읽지 못해 태스크 순서로 그렸습니다" 한 줄과 모델 원문(접기 기능)을 함께 제공합니다.
3. `workflow` 필드가 전달되지 않은 경우에도 2와 동일하게 선형 다이어그램 생성 및 안내 note를 첨부하며, 불필요한 재시도 횟수를 소모하지 않습니다.
4. 사고 예산 및 서킷 브레이커 카운터는 기존과 동일하게 적용됩니다 (`WORKFLOW_INVALID` 역시 반복 호출 감지 로직의 예외가 되지 않음).

→ **§9 결정 4**: 1의 "반려 후 재요청" 대신 처음부터 2(서버 대체)로 갈지 여부. 반려가 품질은 높지만 모델 호출 횟수가 증가합니다.

### 4.5 마지막 그물: 브라우저의 `mermaid.parse`

브라우저 페이지는 다이어그램 렌더링 전 `mermaid.parse(text)`를 사전 호출합니다. 구문 파싱에 실패하면 원문 텍스트를 `<pre>` 블록으로 표시하고 "다이어그램을 그리지
못했습니다" 한 줄 안내 문구를 노출합니다. 이때도 태스크 목록 조회, 의견 작성 및 승인 기능은 정상 동작합니다. 해당 경로가 실제로 호출되었다면 정규형 출력기(emit)의 잠재 버그를
의미하므로, 프론트엔드는 전용 경로(`POST /api/workflow-failed`)로 장애 내역을 전송하여 `state/workflow_render_failed.jsonl` 감사 로그에 기록합니다 (운영 환경 품질 모니터링).

## 5. 승인 페이지

### 5.1 그리기

- `planning/web/workflow.js`(신규, `PAGE_SCRIPTS`에서 `views.js` 다음)가 다이어그램 렌더링 및 노드 클릭 이벤트를 처리합니다.
  플래그가 `0`이면 해당 스크립트와 mermaid 모두 페이지에 포함되지 않습니다 (`_assemble_page`가 환경설정을 전달받음).
- mermaid.min.js는 **인라인 삽입하지 않고** 고정된 단일 경로 `GET /vendor/mermaid.js`를 통해, 서버 기동 시 메모리에 로드해 둔 바이트를
  `Cache-Control: max-age` 헤더와 함께 서빙합니다. 이유: (1) `_assemble_page`는 `</script` 문자열이 포함된 스크립트를 거부하는데
  번들 라이브러리에 해당 패턴이 포함될 수 있음, (2) 매 페이지 로드마다 3 MB 에셋을 중복 전송하지 않음. 서빙 경로는 오직 하나뿐이며
  URL로 임의 디스크 파일을 탐색하는 코드는 여전히 존재하지 않습니다.
- 설정: `mermaid.initialize({startOnLoad:false, securityLevel:'strict', flowchart:{htmlLabels:false}})`, 테마는
  `prefers-color-scheme` 미디어 쿼리에 맞춰 `default`/`dark` 적용 (다크 스킴 지원).
- `mermaid.render()`가 반환한 SVG는 html 템플릿 태그를 거치지 않는 유일한 마크업입니다. strict 모드의 DOMPurify와
  서버 정규화(§4.1)를 기반으로 신뢰성을 확보하며, `html.js`의 `trustedSvg()` 함수로 예외 처리를 일원화합니다.
- 배치 위치: PLAN 승인 카드의 개요 하단, 태스크 목록 상단. 접기/펼치기 토글 지원(기본값: 펼침). 노드가 많을 경우 가로 스크롤 지원.
- 카드 렌더링 서명(`draw`)은 요청 ID에 바인딩되므로 SVG 다이어그램은 요청당 최초 1회만 렌더링 후 캐시됩니다. 주기적 폴링이 다이어그램을 불필요하게 다시 그리지 않습니다 (3.1 "One card at a time").

### 5.2 노드에 의견 달기

```
┌ 워크플로우 ─────────────────────────────────────┐
│  (시작) → [T1 매출 파일 읽기] → ◇D1 Q3 데이터? ─예→ [T2 집계] → [T3 요약] → (종료) │
│                                    └아니오→ (종료)                                │
└──────────────────────────────────────────────┘
  노드를 누르면 의견을 남길 수 있습니다.
  ◇ D1 · Q3 데이터가 있나?     [ 데이터가 없으면 Q2로 대신해 주세요            ]  [지우기]
  워크플로우 전체 의견          [                                              ]
```

- 노드(`g.node`)를 클릭하면 다이어그램 하단에 해당 노드의 검토 의견 입력창이 열립니다. 키보드 접근성 지원: 노드마다 `tabindex=0`,
  `role=button`, `aria-label="D1 Q3 데이터가 있나? 의견"`.
- 검토 의견이 작성된 노드는 테두리를 시각적으로 강조합니다 (기존 `filled` 표시와 동일한 색상 체계).
- **엣지(연결선)에도 의견을 작성할 수 있게 할 것인가** → **§9 결정 5.** 권장: v1은 개별 노드 + "워크플로우 전체 의견" 입력창만 지원합니다. 엣지에 대한
  수정 요구는 "D1에서 '아니오'일 때 …"처럼 노드 의견이나 전체 의견을 통해 충분히 표현 가능합니다.
- `T` 노드에 작성한 의견은 **해당 태스크 행의 의견 입력창과 동일한 데이터**로 연동 처리됩니다 (동일한 draft 키 `…:<request>:<task_id>` 공유).
  다이어그램의 노드에서 입력하든 태스크 행에서 입력하든 양방향 동기화되어 표시됩니다. 단일 태스크에 두 개의 서로 다른 의견 입력창이 존재할 경우
  최종 전달 내용이 모호해지는 문제를 방지합니다.
- 작성 중인 초안은 `localStorage`(`planning-mcp:draft:<request_id>:wf:<node_id>`)에 안전하게 보존됩니다 (D22: 리렌더링·새로고침·탭 간 실시간 동기화).

### 5.3 버튼이 결과를 먼저 말한다

기존 UI 규칙(3.1)을 일관되게 확장 적용합니다. 검토 의견이 입력되는 즉시 `승인` 버튼이 사라지고 수정 요청 버튼이 표시됩니다.

| 작성 내용 | 버튼 (제목 / 세부 내역) | `scope` |
|---|---|---|
| 없음 | `승인` | — |
| 태스크 3에만 작성 (행 또는 T3 노드) | `수정 요청` / `3번만` | `TASKS` (3.2와 동일) |
| 비태스크 노드(D1, S, E) 또는 워크플로우 전체 칸 | `수정 요청(워크플로우)` / `노드 1개` | `WORKFLOW` |
| 위 항목 + 태스크 3 | `수정 요청(워크플로우)` / `노드 1개` / `3번 태스크` | `WORKFLOW` |
| 계획 전체 칸 작성 또는 ☐ 계획 전체를 다시 세우기 선택 | `수정 요청` / `계획 전체 재작성` | `PLAN` |
| … + 완료 기준 수정 | 한 줄 추가: `태스크 완료 기준 1건 반영` / `… 전달` | 위와 동일 |

수정 범위 우선순위는 `PLAN > WORKFLOW > TASKS` 순입니다. `scopeOf()` 판정 함수에서 이 순서대로 스코프를 확정하고 버튼 라벨 역시 동일 함수에서
생성되므로, 사용자에게 노출되는 버튼 라벨과 실제 요청 스코프가 불일치할 위험이 없습니다 (3.1과 동일한 결정론적 보장). 서버는 클라이언트가 전달한 명시적 scope 값을 그대로 처리하며 임의로 추론하지 않습니다.

### 5.4 다시 승인할 때

수정 요청 후 다시 제출된 PLAN 카드의 다이어그램에서는 **변경된 노드**(신규 추가된 노드 또는 라벨이 수정된 노드)를 시각적으로 강조 표시하고, 이전 차수에서 사용자가
의견을 남겼던 노드에는 "요청하신 내용: …"을 하단 안내 문구로 함께 노출합니다. 이를 통해 사용자가 자신이 요청한 피드백이 모델에 의해 정확히 반영되었는지 한눈에
검증할 수 있습니다 (1.13 rework 기능의 `이전 결과` 안내와 동일한 맥락).

### 5.5 다른 카드 (선택: 3.3의 두 번째 단계)

- **실행 카드**: 동일한 다이어그램에 태스크 진행 상태별 색상(대기/진행중/완료/실패, `classDef`는 서버가 주입)을 표시하여 사용자가 전체 진행 상황을 직관적으로 파악.
- **완료 보고**: 전체 완료 색상 적용 + 재작업 요청 노드 강조 표시.
- **정지 카드**: 초안 다이어그램 읽기 전용 제공.

1단계(PLAN 승인 카드 지원)만으로 요구된 핵심 기능은 완성됩니다. 2단계는 동일한 렌더러에 상태 색상만 적용하면 되지만, 실행 카드는 태스크 진행마다 다이어그램을
다시 렌더링해야 하므로(서명이 `rev`로 갱신됨) 성능 비용을 고려하여 후속 단계로 분리합니다 → **§9 결정 6.**

## 6. 서버 쪽 수정 요청 흐름

### 6.1 기록

`ApprovalStore.record_decision`: `SCOPES`에 `SCOPE_WORKFLOW = "WORKFLOW"` 추가. 페이지가
`workflow_comments: {"D1": "...", "*": "전체 의견"}`을 전송합니다. **렌더링된 다이어그램에 존재하지 않는 노드 ID가 하나라도 있으면
결정 전체를 거부**합니다 (`validate_page_choices`·`validate_page_criteria`와 동일한 무결성 검증 기준 적용 — 브라우저 탭 세션 불일치 또는 위조 방지).
`T` 노드에 작성된 의견은 페이지가 이미 `comments`(태스크 의견)로 매핑하여 전송하므로 `workflow_comments`에 `T*` 식별자는 포함되지 않습니다.

`_mutate_no`(scope를 읽는 유일한 곳):

```python
plan.pending_revision = {
    "origin": "workflow",
    "workflow_targets": {"D1": "데이터가 없으면 Q2로", "*": "..."},
    "targets": {3: "..."},          # 태스크 의견이 있을 때만
}
```

완료 기준을 수정한 상태에서 제출된 경우 TASKS와 동일하게 태스크에 즉시 반영합니다 (태스크 목록이 유지되기 때문). 선택된 대안 역시 TASKS와 동일하게 처리합니다.

### 6.2 모델이 받는 힌트

```
The user commented on the workflow.
  D1 "Q3 데이터가 있나?": "데이터가 없으면 Q2로 대신해 주세요"
Call plan_and_think with workflow=<the whole revised flowchart>. Keep T1..T3.
If a change needs a new or removed task, send the full task_list too.
```

태스크 의견도 있으면 기존 `task_updates=[{"task_id": 3, "title": "..."}]` 한 줄이 뒤에 붙습니다.

### 6.3 모델의 답

| 모델이 보낸 것 | 처리 방식 |
|---|---|
| `workflow` (+ 검토 의견이 작성된 태스크의 `task_updates`) | 정상 처리. 기존 태스크 ID·순서·결과 유지. lint 검증 통과 후 신규 PLAN 요청 카드 표시 |
| `workflow` + 전체 `task_list` | 수락 및 안내 note 첨부, audit 로그 `workflow_replanned` 기록 (구조적 변경이 요구된 경우. 토큰 비용이 발생할 수 있으나 사용자 재승인을 거치므로 안전) |
| `task_updates`만 전송, `workflow` 누락 | `REVISION_INCOMPLETE` 반환, 힌트에 필수 인자 안내 |
| `workflow`의 정규형이 이전과 동일함 | `REVISION_INCOMPLETE` 반환 ("the workflow is unchanged") — 사용자 요청 사항 미반영 판단 |
| 검토 의견이 없는 태스크를 임의 수정한 `task_updates` | 기존과 동일하게 무시 및 안내 note 첨부 |

`workflow`만으로 기존 3.0 경로(`pending_revision`, `REVISION_NOT_REQUESTED` 등)와 일관된 구조를 가지므로 신규 오류 코드는
`WORKFLOW_INVALID` 하나뿐입니다.

## 7. 플래그 0의 동일성 보장

"0(기본값) 설정 시 기존 버전과 바이트 단위로 동일함"을 테스트로 보증합니다.

- `build_tool_definitions(..., advanced_workflow=False)` 호출 결과가 3.2 스냅샷과 일치 (모든 실행 모드 조합).
- `page_html()` 생성 결과가 3.2와 바이트 단위로 일치 (workflow.js 및 mermaid 서빙 경로 미포함).
- `/vendor/mermaid.js`는 404 응답 반환.
- 동일한 plan에 대한 지문(fingerprint) 계산 결과가 기존 3.2와 일치.
- `workflow` 필드가 전달되어도 무시 및 안내 note 첨부, 계획 상태 전이 없음.
- `vendor/` 디렉터리가 부재해도 서버 정상 기동 및 전체 테스트 통과.

## 11. 구현 결과 (2026-11-16)

§9의 권장안 7건을 그대로 적용했습니다. 설계와 다른 점과 구현하며 정한 것은 다음과 같습니다.

| 항목 | 내용 |
|---|---|
| 공백 있는 노드 ID | 설계(§4.4) 단계에서는 반려 대상이었으나 모델의 작성 의도가 명확하므로 **자동 보정(수리)** 처리로 개선했습니다. 예를 들어 `데이터 확인 --> T1` 구문은 라벨이 "데이터 확인"인 신규 노드 `N1`으로 자동 변환됩니다. |
| 비ASCII·예약어 노드 ID | 모두 안전한 대체 ID(`N1`…, `end`는 `E`)로 자동 변환하고 라벨 텍스트는 원본을 유지합니다. |
| `T` 노드를 다른 ID로 정의한 경우 | 라벨 텍스트가 태스크 제목과 일치하면 해당 태스크 노드로 자동 매핑합니다 (`A["매출 파일 읽기"]` → `T1`). |
| 플래그 0의 페이지 | 3.2와 **바이트 단위로 동일**(SHA-256 비교로 확인). `workflow.js`는 다른 스크립트를 고치지 않고 함수를 감싸는 방식으로 확장하며, `decide`의 사본은 테스트로 원본과 대조합니다. |
| mermaid 버전 | 11.4.1 (`vendor/manifest.json`에 SHA-256 고정). |
| 변경된 노드 식별 기준 | 노드 ID가 아닌 라벨 텍스트의 변경 여부로 판정합니다. 모델이 ID만 수정한 노드(`start` → `S`)는 변경 노드로 강조하지 않습니다. |
| 렌더 실패 기록 | `/api/control` 대신 전용 경로 `POST /api/workflow-failed` → `state/workflow_render_failed.jsonl`. |
| `requirements.txt` | 만들지 않았습니다 (결정 1). |

**검증**

- 단위 테스트: `test_workflow_lint.py`(40), `test_workflow_revision.py`(28), `test_workflow_page.py`(17), 스모크 `smoke_workflow.py`. 기존 테스트는 변경 없이 모두 통과.
- 브라우저(실제 서버 연동): 자동 보정된 워크플로우 다이어그램 렌더링, 노드 클릭 시 의견 작성창 연동, 버튼 라벨 전환(`수정 요청(워크플로우) / 노드 1개 / 3번 태스크`), 페이지 새로고침 후 초안 유지 검증, 대기 중인 에이전트로 WORKFLOW 수정 요청 정상 전달, 재작성된 카드의 변경 노드 및 이전 요청 내역 표시, 다크 모드 지원, mermaid 에셋 부재 시 원문 텍스트 대체(저하 모드) 동작 검증 완료.
- 실제 파서: lint 코퍼스와 퍼징 결과의 정규형 611건을 브라우저에서 mermaid 11.4.1로 파싱 → 처음 12건 실패(백틱으로 시작하는 라벨, [D34](../wiki/09-defects-and-lessons.md#d34)) → 수정 후 611건 모두 통과, 표본 62건 렌더링 통과.

**향후 과제 (운영 환경 검증)**: 사내 모델이 별도 프롬프트 지시 없이도 `workflow` 필드를 자발적으로 전송하는지, 반려 발생 빈도와 주요 원인, 워크플로우 수정 요청에 대해 다이어그램 재작성으로 응답하는지 또는 전체 재수립으로 처리하는지 등을 [wiki 11](../wiki/11-status-and-next-steps.md)의 감사 이벤트를 통해 지속적으로 모니터링합니다. 실행 카드 및 완료 보고 카드에 작업 상태별 색상을 입힌 다이어그램 시각화(결정 6)는 후속 마일스톤에서 진행할 예정입니다.
