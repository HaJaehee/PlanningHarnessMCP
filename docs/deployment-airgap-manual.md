# 폐쇄망 반입·배포 매뉴얼

개인 PC(`D:\PlanningHarnessMCP`)에서 개발한 planning-mcp 패키지를 사내 폐쇄망 환경으로
안전하게 이관하여 AnythingLLM에 연동하기까지의 전체 절차를 안내합니다.

---

## 0. 전제와 범위

**본 문서에서 다루는 내용**
- 반입 대상 파일과 반입 제외 파일의 기준
- 반입 패키지 생성 및 반입 후 무결성(해시값) 검증 방법
- 사내 폐쇄망 PC에서의 설치, 무결성 검증, AnythingLLM 등록 절차
- 사내 정보보안 심사 요청 시 첨부할 증빙 자료 작성법

**본 문서에서 다루지 않는 내용**
- 사내 보안 반입 정책 자체. 보조기억매체 반입, 망연계 전송, 소프트웨어 반입 승인은 **소속 기관의 공식 보안 규정을 엄격히 준수하십시오.**
  본 매뉴얼은 보안 절차의 우회가 아닌, 보안 심사에 필요한 객관적 증빙 자료를 사전에 빈틈없이 갖추도록 돕는 데 목적이 있습니다.

**핵심 특성 3가지** — 보안 심사 및 반입 난이도를 결정짓는 요소

| 구분 | 내용 |
|---|---|
| 크기 | 약 **80 KB**, 파일 25개 (파이썬 인터프리터 동봉 시 약 **11 MB**) |
| 파일 형식 | 소스코드가 **100% 순수 평문(Plaintext)** 텍스트 (`.py`, `.md`, `.json`) |
| 외부 의존성 | **외부 라이브러리 0개**. Python 표준 라이브러리만 사용 → 사내 폐쇄망에서 `pip install` 불필요 |

즉, 실제 반입 대상은 "사람이 육안으로 직접 검증 가능한 80KB의 평문 텍스트"입니다. 이러한 투명성이 보안 심사 통과의 가장 큰 강점이므로, 임의로 압축 암호를 설정하거나 파일 확장자를 변경하여 내용을 가리지 마십시오.

반입 패키지는 **두 가지 형태**로 생성할 수 있습니다:

- **기본 패키지** — 순수 소스코드만 포함. 사내 PC에 Python 3.9 이상이 이미 설치되어 있어야 합니다.
- **인터프리터 동봉 패키지** — python.org 공식 임베디드 배포판(Embeddable package)을 함께 패키징합니다. **사내 PC에 Python이 설치되어 있지 않거나 관리자 설치 권한이 없는 환경**에서도 압축 해제만으로 즉시 구동됩니다 (자세한 내용은 §3 참조).

## 1. 반입 대상 목록

### 반입 대상 파일 (패키징 스크립트가 자동 선별)

| 파일 경로 | 내용 및 용도 |
|---|---|
| `server.py` | MCP 서버 메인 진입점 |
| `planning/*.py` | 서버 핵심 구현체 (10개 모듈) |
| `tests/*.py` | 단위 테스트 및 stdio 종단 간(E2E) 스모크 테스트 |
| `tools/*.py` | 패키징 및 사내 환경 검증 스크립트 |
| `docs/*.md` | Phase 1~4 설계 아키텍처 문서 및 본 배포 매뉴얼 |
| `README.md`, `.gitignore` | 프로젝트 개요 및 형상 관리 설정 파일 |
| `anythingllm_mcp_servers.example.json` | AnythingLLM MCP 서버 등록 예시 설정 |

| `runtime/` | **`--with-python` 옵션 사용 시에만 포함.** python.org 공식 임베디드 배포판 zip(원본 그대로) 및 출처 명시용 `RUNTIME.md` |

### 반입 제외 대상 및 제외 사유

| 제외 대상 | 제외 사유 |
|---|---|
| `state/` | **개인 PC에서 테스트했던 실제 계획 데이터**가 평문으로 저장되어 있습니다. 사내 PC에서 구동 시 새로 생성되므로 이관할 필요가 없으며, 포함될 경우 불필요한 개인 테스트 데이터까지 보안 심사 대상이 됩니다. |
| `__pycache__/` | 컴파일된 파이썬 바이트코드(`.pyc`)는 보안 검토자에게 분석 불가능한 불투명 바이너리로 인식될 수 있습니다. 소스코드가 전량 평문이라는 강력한 장점을 훼손하므로 제외합니다. |
| `.git/` | 커밋 이력에 로컬 개발 절대 경로, 사용자 계정명, 과거 삭제 파일 이력 등이 남아 보안 검토 시 불필요한 질의를 유발할 수 있습니다. |
| `dist/` | 패키징 빌드 산출물 폴더 (자기 참조 및 중복 압축 방지) |

### 사전 확인이 필요한 파일: `CLAUDE.md`

프로젝트 개발 지침서로서 사내 유지보수 시 유용한 문서이나, 외부 AI 도구를 활용해 설계되었다는 맥락이 기재되어 있습니다. **소속 기관의 외부 AI 활용 및 산출물 반입 규정을 사전에 확인하십시오.** 패키징 스크립트 기본 설정에서는 제외되어 있으며, 포함하고자 할 경우 `tools/make_package.py`의 `INCLUDE_FILES` 목록에 추가하십시오.

## 2. 개인 PC에서 수행할 작업 — 패키지 생성

### 2-1. 반입 전 최종 사전 검증

오류가 있는 코드를 반입하면 인터넷 검색이나 외부 자료 조회가 불가능한 폐쇄망 환경에서 직접 디버깅해야 하는 큰 곤란을 겪게 됩니다. 반드시 개인 PC 환경에서 다음 테스트를 모두 통과시킨 후 패키징을 진행하십시오.

```bash
python -m unittest discover -s tests
```

```bash
python tests/smoke_stdio.py
```

각각 `Ran 49 tests ... OK`, `All smoke checks passed.` 결과가 출력되어야 합니다.

### 2-2. 패키지 생성 스크립트 실행

```bash
python tools/make_package.py
```

실행 시 `dist/planning-mcp-1.0.0-<날짜>.zip` 압축 파일과 루트 경로의 `MANIFEST.txt`가 생성되며, 콘솔 마지막 줄에 패키지 전체의 SHA-256 체크섬이 출력됩니다.

### 2-3. 체크섬을 패키지 아카이브 외부에 별도 보관

이는 폐쇄망 반입 실무에서 가장 빈번하게 누락되는 핵심 단계입니다. 해시값이 압축 아카이브 내부에만 존재할 경우 무결성 검증의 신뢰성을 담보할 수 없습니다. 출력된 SHA-256 체크섬을 **반입 매체와 분리된 다른 경로**(예: 사내 메신저, 별도 메모, 인쇄물 등)를 통해 사내로 전달하십시오.

사내 PC에서 압축을 풀기 **전에** 다음 명령으로 파일 해시를 대조하십시오:

```powershell
Get-FileHash .\planning-mcp-1.0.0-20260724.zip -Algorithm SHA256
```

해시값이 일치하지 않는다면 전송 중 파일이 손상되었거나 망연계 보안 솔루션에 의해 파일이 변조된 것입니다. 이 경우 압축을 해제하지 말고 패키지를 다시 반입하십시오.

## 3. 사내 PC의 Python 환경 — 인터프리터 동봉 권장

외부 의존성 패키지가 전혀 없으므로 고려해야 할 실행 환경 변수는 **파이썬 인터프리터 하나뿐**입니다. 그리고 이 인터프리터마저 패키지에 안전하게 동봉할 수 있습니다. **사내 PC에 Python이 설치되어 있지 않거나 관리자 설치 권한이 없는 환경에서도 완벽히 동작합니다.**

### 3-0. 두 가지 배포 방식 비교

| 비교 항목 | 사내 시스템 Python 활용 | **인터프리터 동봉 배포 (권장)** |
|---|---|---|
| 패키지 파일 크기 | 약 80 KB | 약 **11 MB** |
| 사내 PC 사전 요구사항 | Python 3.9 이상 기설치 필수 | **사전 설치 요구사항 없음** |
| 관리자(Admin) 권한 | 파이썬 신규 설치 시 권한 필요 | 관리자 권한 불필요 (단순 압축 해제) |
| 보안 반입 심사 대상 | 100% 순수 평문 텍스트 | 순수 평문 + 공식 원본 바이너리 1개 |
| 기존 업무 환경 간섭 | 시스템 전역 파이썬 환경 공유 | 완전 격리 (디렉터리 삭제 시 흔적 없이 제거) |

사내 PC의 파이썬 설치 여부가 **조금이라도 불확실하다면 인터프리터를 동봉하십시오.** 사내 폐쇄망에 진입한 뒤 파이썬 부재를 인지하게 되면 전체 반입 절차를 처음부터 다시 진행해야 하므로, 불과 11 MB의 용량을 아끼려다 수일의 배포 일정을 낭비하게 됩니다.

사내 PC의 파이썬 설치 여부를 사전 확인하는 명령:

```powershell
python --version
```

```powershell
py -0
```

### 3-1. 임베디드 배포판 다운로드 (개인 PC, 인터넷 환경)

python.org → Downloads → Windows → **"Windows embeddable package (64-bit)"**
다운로드 파일명은 `python-3.12.x-embed-amd64.zip` 형태이며 크기는 약 11 MB입니다.

다운로드 직후 **공식 웹페이지에 명시된 SHA-256 체크섬을 기록**하십시오. 보안 심사 시 인터프리터의 무결성과 출처를 증명하는 핵심 근거가 됩니다.

```powershell
Get-FileHash .\python-3.12.10-embed-amd64.zip -Algorithm SHA256
```

> **PyInstaller 단일 실행 파일(`.exe`) 방식을 사용하지 않는 이유**
> 소스코드 전체가 단일 바이너리로 묶이게 되면 내부 로직 분석이 불가능해져 보안 심사가 극도로 까다로워지며, 사내 엔드포인트 보안 솔루션(EDR/백신)에서 악성코드로 오탐되어 차단되는 사례가 빈번합니다. 반면 임베디드 배포판 방식은 **인터프리터만 공식 인증된 바이너리이고 실제 애플리케이션 코드는 100% 평문 그대로 보존**되므로, 보안 담당자가 모든 동작을 투명하게 직접 열람하고 검증할 수 있습니다.

### 3-2. 인터프리터를 포함한 패키징 실행 (개인 PC)

```bash
python tools/make_package.py --with-python C:\dl\python-3.12.10-embed-amd64.zip
```

실행 완료 시 `dist/planning-mcp-1.0.0-<날짜>-with-python.zip` 아카이브가 생성됩니다.

패키징 스크립트는 임베디드 zip 파일을 **원본 그대로(Verbatim, 무압축 원형 보존)** 패키지 내부에 저장합니다. 임의로 압축을 해제하거나 재압축, 파일 수정을 가하지 않습니다. 그래야 보안 검토자가 python.org 공식 웹사이트에 공표된 SHA-256 체크섬과 1:1로 직접 대조하여 인터프리터의 위·변조 여부를 확실히 검증할 수 있기 때문입니다. 상세 출처 정보는 패키지 내 `runtime/RUNTIME.md` 파일에 자동 생성됩니다.

또한 공식 임베디드 배포판 규격(`python.exe`, 표준 라이브러리 zip 파일, `._pth` 경로 파일 존재)에 부합하는지 엄격히 검증하며, 유효하지 않은 파일이 지정될 경우 패키징이 자동으로 중단됩니다.

### 3-3. 사내 PC에서의 파이썬 런타임 초기화

**사내 PC에 기존 파이썬이 이미 설치되어 있는 경우** — 다음 명령 한 줄로 초기화가 완료됩니다:

```powershell
python tools\setup_runtime.py
```

**사내 PC에 파이썬이 전혀 설치되어 있지 않은 경우** — Windows 기본 파워셸 명령으로 인터프리터 압축을 해제한 후, 해당 인터프리터로 초기화 스크립트를 실행합니다:

```powershell
Expand-Archive .\runtime\python-3.12.10-embed-amd64.zip -DestinationPath .\runtime
```

```powershell
.\runtime\python.exe tools\setup_runtime.py
```

이 절차가 실제 폐쇄망 환경에서 완벽히 검증된 실행 경로입니다. 이후 안내되는 **모든 실행 명령에서는 `.\runtime\python.exe`를 사용**하십시오.

초기화 스크립트가 수행하는 작업은 다음 두 가지로 매우 단순합니다:
1. embed zip 파일을 `runtime/` 폴더에 압축 해제
2. `python312._pth` 파일에 상위 경로(`..`) **한 줄 추가**

2번 작업이 필요한 이유: 파이썬 공식 임베디드 배포판은 독립 격리 모드로 기본 구동되므로, 현재 디렉터리를 `sys.path`에 자동으로 포함하지 않으며 환경변수 `PYTHONPATH`도 무시합니다. 따라서 상위 디렉터리(`..`) 참조가 추가되지 않으면 `import planning` 모듈 임포트가 실패하게 됩니다. (이 수정 사항은 일반 텍스트 파일인 `._pth`에 한 줄로 명시되므로 보안 검토자가 육안으로 쉽게 확인할 수 있습니다. 아울러 `server.py` 진입점 내부에도 동일 문제를 방어하는 이중 안전장치가 구현되어 있습니다.)

### 3-4. 인터프리터를 동봉하지 않고 기존 사내 Python을 활용하는 방안

**A. 사내 소프트웨어 카탈로그를 통한 정식 승인 파이썬 설치**

신청 및 결재에 시일이 소요되므로 **코드 반입 신청과 동시에** 선제적으로 요청하십시오.

**B. 타 업무 도구에 번들 설치된 기존 Python 경로 활용**

```powershell
Get-ChildItem C:\ -Recurse -Filter python.exe -ErrorAction SilentlyContinue -Depth 4 |
  Select-Object -First 10 FullName
```

사내 PC에서 적합한 파이썬 실행 파일을 찾았다면 해당 절대 경로를 AnythingLLM 설정의 `command` 항목에 지정하면 됩니다. 단, 타 소프트웨어에 번들된 인터프리터를 별도 프로세스로 전용하는 행위가 사내 소프트웨어 사용 규정에 위배되지 않는지 사전에 확인하십시오.

## 4. 반입 매체 및 보안 심사 실무 가이드

소속 기관의 표준 반입 절차를 준수하되, 다음은 폐쇄망 반입 실무에서 흔히 마주치는 주요 이슈와 해결 방안입니다.

- **압축 파일(zip) 반입이 원천 차단되는 경우**: 임의로 확장자를 변경하거나 암호를 걸어 우회 반입을 시도하지 마십시오. 이는 명백한 보안 규정 위반이며, 본 패키지에는 은폐할 코드가 없습니다. 반입이 차단될 경우 보안 담당 부서에 **전체 파일이 24개의 순수 평문 텍스트 소스코드**임을 소명하고 공식적으로 허용된 반입 절차를 안내받으십시오.
- **`.py` 확장자 파일이 실행 스크립트로 분류되어 차단되는 경우**: 역시 정식 보안 질의 및 심사 대상입니다. 설계 아키텍처 문서(`docs/*.md`)를 함께 첨부하여 업무 목적과 안전성을 소명하면 승인이 훨씬 수월합니다.
- **Mark of the Web (Zone.Identifier 차단)**: 인터넷, 메일, 보조기억매체를 거친 파일에는 Windows 운영체제에 의해 실행 차단 보안 플래그가 자동 부여될 수 있습니다. 압축을 해제한 직후 다음 명령을 실행하여 차단을 일괄 해제하십시오:

  ```powershell
  Get-ChildItem -Recurse -Path .\planning-mcp | Unblock-File
  ```

- **엔드포인트 보안(백신/EDR) 정책**: AnythingLLM 데스크톱 앱이 `python.exe`를 하위 자식 프로세스로 실행하고 표준 입출력(stdio) 파이프로 통신하는 구조로 인해 행위 기반 탐지 차단이 발생할 수 있습니다. 반입 신청서에 이러한 프로세스 간 파이프 통신 구조를 미리 명시해 두면 보안 부서와의 소통 및 예외 승인이 한결 원활해집니다.

**승인 웹 UI(내장 웹 서버)에 대한 보안 보충 설명**

- **추가 외부 의존성이 전혀 없습니다.** 웹 서버는 Python 표준 라이브러리인 `http.server`를 사용하며, UI 화면(HTML/CSS/JS)은 `planning/approval.py` 내부에 문자열 상수로 인라인 임베딩되어 있습니다. 별도의 정적 파일 폴더나 웹 번들러, 외부 CDN 조회가 일절 없으며, 반입 산출물은 여전히 100% 순수 파이썬 평문 코드뿐입니다.
- **통신 방향은 로컬 인바운드 전용입니다.** 본 서버는 승인 요청을 수신하기만 할 뿐 외부 네트워크로 어떤 패킷도 발신하지 않습니다 (아웃바운드 호출 0건은 상기 검증 명령으로 증명 가능).
- **사내 보안 정책(방화벽/EDR)에 미리 공지하십시오.** 로컬 프로세스가 수신 대기(Listening) 소켓을 여는 행위가 사내 보안 관제 정책상 신고 대상일 수 있습니다. 외부 네트워크 접근이 차단된 로컬 루프백(`127.0.0.1`) 전용 소켓임을 소명하면 예외 승인이 수월합니다.
- 포트가 이미 타 프로세스에 의해 점유되어 있다면 다음 번호 포트로 자동 이동하며, 허용 대역 전체 바인딩에 실패할 경우 **경고를 응답에 포함**하여 하드 일시정지 가드가 비활성화되었음을 명확히 알립니다(감사 로그 `approval_ui_unavailable`).
- 승인 UI는 **서버 시작 즉시** 포트를 바인딩합니다. 서버 초기 기동 로그를 확인하는 시점에 바인딩 성공 여부를 즉시 파악할 수 있도록 하여, 실제 승인 요청 도중에 알 수 없는 원인으로 승인 기능이 무력화되는 사태를 방지합니다.

### 승인 웹 페이지 권장 운용 수칙 (팝업에 의존하지 않는 안정적인 운용법)

브라우저 자동 실행은 최선의 편의 기능(Best-effort)일 뿐입니다. 사내 보안 정책, 기본 브라우저 미지정, 다중 모니터 환경 등에 의해 팝업 창이 가려지거나 차단될 수 있습니다. **가장 안정적인 권장 운용법은 브라우저 탭을 사전에 하나 열어두는 것입니다:**

1. 서버 시작 로그에서 웹 UI 주소 확인: `APPROVE PLANS AT -> http://127.0.0.1:8765/`
2. 해당 주소를 웹 브라우저 탭으로 열어둔 채 **상시 유지**합니다.
3. 에이전트로부터 승인 요청이 접수되면 탭 제목이 `⚠ 승인 대기 중`으로 깜빡이고 짧은 알림음이 울립니다.

**사용자가 촉박하게 서두를 필요가 없습니다.** 대다수 LLM 클라이언트는 단일 도구 호출이 60초를 넘길 경우 타임아웃 오류를 발생시키고 실행을 중단하므로, 서버는 45초 주기로 자체 슬라이스를 끊어 반환하고 에이전트가 곧바로 다음 대기 호출을 이어가도록 설계되었습니다. 사용자 화면에서는 아무런 영향이 없습니다. **승인 대기 웹 페이지는 사용자가 결정을 내릴 때까지 닫히지 않고 유지**되며, 승인/반려 버튼을 누르면 다음 슬라이스 주기(최대 45초 이내)에 에이전트 대화가 자연스럽게 재개됩니다 (전체 최대 대기 시간은 15분).

각 승인 카드에 표시되는 상태의 의미:

- **에이전트가 대기 중입니다** — 승인/반려를 결정하시면 에이전트가 즉시 다음 작업을 진행합니다.
- **에이전트가 대기를 멈췄습니다** — 사용자의 결정은 서버에 안전하게 반영되지만(감사 로그 `late_decision_applied`), 채팅창에 추가 메시지를 하나 입력해 주셔야 에이전트가 다음 턴을 시작하여 진행합니다.

작성 중이던 수정 의견은 다른 세션의 승인 요청이 추가되거나, 페이지를 새로고침하거나, 브라우저를 닫았다가 다시 열어도 그대로 보존됩니다. 브라우저 탭을 여러 개 열어둔 경우 어느 탭에서 입력하더라도 모든 탭에 실시간으로 동일하게 반영됩니다.

단, 그사이 에이전트가 계획을 새로 수정하여 제출한 경우 사용자가 확인하지 않은 과거 계획에 이전 결정이 잘못 적용되지 않도록 기존 승인 대기는 자동으로 무효화 및 폐기됩니다.

승인 URL은 채팅창에 출력되는 계획 안내 메시지 하단에도 함께 표시됩니다(`승인/거절: http://...`). 실수로 브라우저 탭을 닫았더라도 채팅창 링크를 클릭해 언제든 다시 접속할 수 있습니다.

**인터프리터를 동봉하는 경우 추가로 소명할 점**

- 약 11 MB의 **바이너리 파일**(python.exe, DLL, .pyd)이 포함되므로 "전부 평문 텍스트"라는 장점이 해당 파일들에는 적용되지 않습니다. 따라서 보안 심사 기간을 며칠 더 넉넉히 잡으십시오.
- 대신 공식 원본을 그대로 포함하므로 **출처와 무결성을 수치로 완벽히 입증**할 수 있습니다. python.org 공식 공표 SHA-256 해시값과 일치하므로 Python 소프트웨어 재단에서 공식 배포한 원본과 비트 단위로 동일함을 증명할 수 있습니다.
- 설치 과정에서 이루어지는 유일한 로컬 변경 사항은 `python312._pth` 파일에 `..` **한 줄을 추가하는 것뿐**이며, 일반 텍스트 파일이므로 누구나 확인할 수 있습니다.
- 동봉된 인터프리터는 `runtime/` 폴더 외부에 어떠한 파일도 쓰지 않으며, 시스템 환경변수(PATH)나 레지스트리를 전혀 수정하지 않아 기존 사내 파이썬 환경과 완벽히 격리됩니다.

### 보안 심사 시 필수 고지 사항: 계획 데이터의 로컬 평문 저장

**계획 및 실행 기록은 `state/plan_state.json` 파일에 평문으로 저장됩니다.**

사용자가 에이전트에게 지시한 최종 목표, 세부 태스크 제목, 도구 실행 결과 로그가 로컬 파일에 그대로 기록됩니다. 따라서 사내 기밀 업무나 민감 정보가 포함된 대화를 수행할 경우 해당 텍스트가 로컬 디스크에 평문으로 축적됩니다. 이는 설계상의 결함이 아니라 관리자가 언제든 직접 검증할 수 있도록 의도된 투명성 설계 원칙입니다. 따라서 다음 사항을 함께 안내하고 조치하십시오:

- `state/` 디렉터리를 사내 보안 규정상 적절한 접근 제어가 적용되는 안전한 경로에 배치하십시오 (`PLANNING_MCP_STATE_DIR` 환경변수로 지정 가능).
- 해당 PC의 디스크 암호화(BitLocker 등) 정책이 적용되는 드라이브인지 확인하십시오.
- `state/audit.jsonl` 파일은 추가 전용(Append-only) 감사 로그로 지속적으로 누적됩니다. 사내 로그 보존 및 폐기 정책에 따라 주기적 정리 대상에 포함하십시오.

### 6-4. AnythingLLM MCP 서버 등록

설정 파일은 일반적으로 다음 경로에 위치합니다 (정확한 파일 경로는 AnythingLLM 데스크톱 앱의
**Agent Skills → MCP Servers** 화면 상단에 명시되므로 해당 위치를 확인하십시오):

```
%APPDATA%\anythingllm-desktop\storage\plugins\anythingllm_mcp_servers.json
```

`anythingllm_mcp_servers.example.json` 파일을 참고하여 설정을 작성합니다.
**인터프리터를 동봉한 경우**(권장 기본값):

```json
{
  "mcpServers": {
    "planning": {
      "command": "D:/planning-mcp/runtime/python.exe",
      "args": ["-u", "D:/planning-mcp/server.py"],
      "env": {
        "PYTHONUTF8": "1",
        "PYTHONUNBUFFERED": "1"
      },
      "anythingLLMAware": true
    }
  }
}
```

`setup_runtime.py` 스크립트 실행 완료 시 마지막 콘솔에 해당 환경에 최적화된 `command` 라인을 완성된 형태로 출력하므로 그대로 복사해 붙여넣으면 됩니다.

**인터프리터를 동봉하지 않고 사내 PC의 파이썬을 사용하는 경우**에는 `command` 항목만 해당 파이썬의 절대 경로로 지정하십시오:

```json
"command": "C:/Program Files/Python312/python.exe"
```

> 예시 파일의 `_README`, `_alternatives` 항목은 안내용 설명 키입니다. `mcpServers` 블록 외부에 위치하므로 삭제하지 않아도 AnythingLLM 동작에 아무런 영향을 주지 않습니다.

JSON 설정 작성 시 필수 주의 사항 (가장 빈번한 오류 발생 구간):

- **경로 구분자는 슬래시(`/`) 사용 권장**: JSON 표준에서 역슬래시(`\`)는 이스케이프 문자이므로 `\\`로 두 번 이스케이프해야 합니다. 실수를 방지하기 위해 일반 슬래시(`/`)를 사용하는 것이 안전합니다.
- **`command`에는 파이썬 실행 파일의 절대 경로 지정**: AnythingLLM 프로세스가 상속받는 시스템 환경변수(PATH)가 현재 터미널과 다를 수 있습니다 (`(Get-Command python).Source` 명령으로 확인 가능).
- **`-u` 옵션 필수 유지**: 표준 입출력 버퍼링이 걸릴 경우 서버가 응답 없이 멈춘 것처럼(hang) 동작하므로 파이썬의 비버퍼링 실행 옵션인 `-u`를 반드시 포함해야 합니다.

설정 파일을 저장한 후 **AnythingLLM 데스크톱 앱을 완전히 종료했다가 다시 실행**하고, Agent Skills → MCP Servers 메뉴에서 `planning` 서버가 실행 중(Running) 상태로 표시되며 4개의 도구가 정상 노출되는지 확인하십시오.

### 6-5. AnythingLLM 워크스페이스 에이전트 환경 설정

1. `docs/phase3-anythingllm-agent-prompt.md`의 **Variant A (영문 시스템 프롬프트)**를 워크스페이스 에이전트 시스템 프롬프트 입력창에 붙여넣기

3. web-search, web-scraping 등 **외부 인터넷 기반 기본 에이전트 스킬 전면 비활성화** (에이전트에게 노출되는 도구 수가 적을수록 소형 모델의 도구 선택 오류가 급감하며, 폐쇄망 환경에서는 인터넷 조회가 어차피 불가능합니다)

## 8. 폐쇄망 반입 환경 특화 문제 해결 (Troubleshooting)

일반적인 런타임 오류 증상은 `docs/phase4-testing-matrix.md` **Part E**(15개 점검 항목)에 정리되어 있습니다. 아래 표는 오직 폐쇄망 반입 직후 설치 환경에서만 특화되어 발생하는 이슈들입니다.

| 발생 증상 | 원인 분석 | 조치 방안 |
|---|---|---|
| SHA-256 해시값 불일치 | 전송 과정 중 파일 손상 또는 보안 망연계 솔루션의 파일 변조 | 압축을 풀지 말고 재반입 수행. 텍스트 줄바꿈(CRLF/LF) 변환에 의한 변조일 수 있으므로 바이너리 모드로 전송되었는지 확인 |
| `verify_install.py`에서 MANIFEST 불일치 오류 | 압축 해제 도중 특정 파일 누락 또는 훼손 | 콘솔에 출력된 훼손 파일명을 확인하고 패키지 재반입 |
| AnythingLLM에서 `spawn ...\runtime\python.exe ENOENT` 에러 | **§6-2 런타임 초기화 단계를 누락함.** 반입 아카이브는 원본 zip을 그대로 담고 있으므로 초기화 전에는 `python.exe`가 없음 | `runtime\` 폴더 내 zip 파일 존재 여부를 확인하고 §6-2 명령 실행. JSON 설정의 `command` 경로는 수정 불필요 |
| `ENOENT` 에러가 발생하나 `runtime\python.exe`는 실제 존재함 | `command` 경로가 실제 설치 드라이브/디렉터리와 불일치 | `setup_runtime.py` 스크립트가 마지막에 출력한 `command` 경로 문자열을 그대로 복사하여 반영 |
| `ModuleNotFoundError: planning` 임포트 실패 | 임베디드 Python의 독립 격리 모드 특성 | `tools\setup_runtime.py` 정상 실행 여부 확인. `runtime\python312._pth` 파일 내에 `..` 경로가 명시되어 있어야 함 |
| `verify_install`에서 "Bundled runtime is set up" 실패 | 임베디드 인터프리터 압축을 아직 해제하지 않음 | §3-3에 안내된 압축 해제 및 셋업 명령 재실행 |
| `verify_install`에서 "Bundled runtime in use" 실패 | 동봉된 전용 파이썬이 아닌 시스템 전역 파이썬으로 검증을 실행함 | 반드시 `.\runtime\python.exe tools\verify_install.py` 명령으로 실행 |
| `setup_runtime` 재실행 시 `PermissionError` 발생 | 현재 실행 중인 파이썬 프로세스 자체를 덮어쓰려 시도함 | 파일 잠금에 의한 정상 방어 동작임. 재초기화가 필요한 경우 타 파이썬으로 `--force`를 주거나 `runtime\` 폴더를 삭제 후 재해제 |
| 승인 웹 UI 화면이 자동으로 열리지 않음 | 브라우저 팝업이 보안 정책에 의해 차단되었거나, **다른 모니터나 백그라운드 창**에 가려진 경우, 또는 기본 웹 브라우저가 지정되지 않은 경우 | **자동 팝업에 의존하지 마십시오.** 서버 시작 시 stderr에 출력되는 `APPROVE PLANS AT -> http://127.0.0.1:<port>/` 주소를 웹 브라우저 탭에 미리 열어두면 됩니다. 해당 탭이 1.5초 주기로 자동 폴링하며, 요청 시 탭 제목 깜빡임과 알림음이 작동합니다. 또한 채팅창의 계획 메시지 하단 링크로도 접속 가능합니다. |
| 콘솔 stderr에 `Approval UI port 8765 was busy` 로그 기록 | 이전 MCP 프로세스 재시작 시 잔류한 이전 `server.py` 프로세스가 포트를 점유 중 | 동작 자체는 차순위 포트로 자동 이동하여 정상 작동함. 다만 과거 프로세스가 동일한 상태 파일을 공유할 우려가 있으므로 프로세스 정리를 권장 |
| `Could not bind the approval UI on ports 8765-8774` 에러 | 허용된 전체 포트 대역이 타 프로그램에 의해 점유됨 | 잔류 프로세스를 종료하거나 환경변수 `PLANNING_MCP_APPROVAL_PORT`로 여유 있는 타 포트 대역 지정 |
| 응답 메시지에 `NOT hard-paused` 경고 출력 | 승인 웹 서버 바인딩 실패로 인해 **하드 일시정지 가드가 비활성화된 상태** | **작업을 진행하지 마십시오.** 상기 원인을 해결하여 승인 UI를 복구한 후 계획을 다시 수립하십시오. |
| 서버는 구동되나 `runtime\python.exe -c "import planning"` 실행만 실패 | embed zip을 수동 재압축 해제하면서 수정되었던 `._pth` 파일이 원본으로 덮어써짐 | `setup_runtime.py` 재실행 (멱등성이 보장되므로 `_pth` 파일만 다시 패치됨). `verify_install.py`로 복구 여부 확인 |
| 시스템에서 `python` 명령어를 찾을 수 없음 | AnythingLLM 구동 환경의 PATH 환경변수 미지정 | JSON 설정의 `command` 항목에 파이썬의 절대 경로 명시 (§3-2 C항목 참조) |
| 서버 프로세스가 시작 즉시 비정상 종료됨 | 설정 경로 오타 또는 역슬래시 이스케이프 오류 | 명령 프롬프트에서 `python D:\planning-mcp\server.py`를 직접 실행해 보아 정상 대기하면 JSON 설정 파일의 문법 오류임 |
| 서버 프로세스가 아무런 응답 없이 대기함 | 표준 출력 버퍼링 발생 | `args`에 `-u` 플래그 추가 및 `env`에 `PYTHONUNBUFFERED=1` 설정 적용 |
| 한글 데이터 입력 시 인코딩 예외 오류 발생 | Windows 콘솔의 기본 CP949 인코딩 충돌 | `env` 설정에 `PYTHONUTF8=1` 환경변수 명시 |
| AnythingLLM 재시작 시 기존 계획 데이터가 소실됨 | 상태 저장소 경로에 쓰기 권한이 없음 | 환경변수 `PLANNING_MCP_STATE_DIR`로 쓰기 권한이 부여된 디렉터리 명시 |
| 백신/EDR에 의해 파이썬 프로세스 생성이 차단됨 | 사내 엔드포인트 보안 정책 위반 탐지 | 사내 정보보안팀에 AnythingLLM 데스크톱 앱의 파이썬 하위 프로세스 호출에 대한 보안 예외 등록 신청 |

사내 폐쇄망 환경에서 원인 분석(디버깅) 시: 1차적으로 `verify_install.py`를 실행하여 환경 무결성을 진단하십시오. 이후 원인 파악이 더 필요할 경우 다음과 같이 `--log-level DEBUG` 옵션을 주어 서버를 직접 실행하고 표준 에러(stderr) 로그를 확인하십시오.

```powershell
python D:\planning-mcp\server.py --log-level DEBUG
```

(콘솔이 입력 대기 상태로 멈추어 있다면 정상 동작입니다. stdio 기반 MCP 서버는 클라이언트와의 표준 입출력 연결을 대기합니다.)

## 9. 패키지 업데이트 반입 절차 (2회차 이후 릴리스)

패키지 전체 용량이 매우 작으므로 변경분(델타)만 추출하기보다 **전체 패키지를 재반입하는 방식이 가장 단순하고 안전**합니다.

업데이트 순서:

1. 개인 PC에서 `python tools/make_package.py` 재실행 (버전이 변경된 경우 `planning/config.py`의 `SERVER_VERSION` 값 수정 확인)
2. 사내 PC에서 기존 **`state\` 디렉터리를 선제적으로 백업**
   ```powershell
   Copy-Item D:\planning-mcp\state D:\planning-mcp-state-backup -Recurse
   ```
3. `state\`를 제외한 나머지 파일들을 덮어쓰기 방식으로 압축 해제
   ```powershell
   Expand-Archive -Path .\planning-mcp-<새버전>.zip -DestinationPath D:\ -Force
   ```
   `.gitignore` 및 패키징 선별 목록에 `state/`가 원천 배제되어 있으므로 아카이브 압축 해제가 기존 상태 데이터를 덮어쓰지 않습니다.
4. `python tools\verify_install.py` 실행 → 최종 GO 판정 확인
5. AnythingLLM 데스크톱 앱 재시작

> 진행 중이던 계획이 존재하는 상태에서 서버를 업데이트하더라도 재시작 후 `get_current_plan` 도구를 호출하면 기존 상태를 안전하게 이어받아 작업을 계속할 수 있습니다. 상태 파일 저장 구조가 변경되는 메이저 업데이트인 경우 `schema_version` 값이 상향되므로 배포 릴리스 노트를 확인하십시오. 현재 버전은 `schema_version: 1`입니다.

## 10. 서비스 제거 및 이전 버전 롤백 절차

Windows 레지스트리, 백그라운드 서비스, 시작프로그램에 어떠한 시스템 설정도 등록하지 않으므로 서비스 제거는 다음 3단계로 완결됩니다:

1. `anythingllm_mcp_servers.json` 설정 파일에서 `"planning"` 서버 설정 블록 삭제
2. AnythingLLM 데스크톱 앱 재시작 (MCP 서버 프로세스는 부모인 AnythingLLM 프로세스에 종속되므로 함께 안전하게 종료됨)
3. 로컬의 `D:\planning-mcp` 배포 디렉터리 삭제

**이전 버전으로 롤백하고자 하는 경우**에는 보관 중인 이전 버전의 아카이브 zip을 다시 압축 해제하여 덮어쓰면 됩니다. 이때 기존 `state\` 폴더는 그대로 유지하십시오.

**모든 계획 이력을 완전 초기화하고자 하는 경우**에는 서버 프로세스를 종료한 뒤 `state\` 폴더를 수동 삭제하십시오. 다음번 서버 실행 시 깨끗한 초기 상태 디렉터리가 자동으로 생성됩니다. 만약 과거 감사 추적 기록이 필요하다면 `audit.jsonl` 파일을 별도로 백업해 두십시오.

## 11. 세션 및 워크스페이스 간 상태 격리 원칙

> **v1.8.0부터 멀티 플랜(다중 계획) 동시 실행이 지원됩니다.** 서로 다른 세션이 각자의 독립적인 계획을 동시에 수행할 수 있으며 서로 간섭하거나 덮어쓰지 않습니다. `plan_and_think` 도구는 `goal` 문자열을 기준으로 계획을 식별 및 라우팅하며(에이전트 시스템 프롬프트가 매 단계 동일한 goal을 반복 전송하도록 강제함), 다른 도구들은 활성 계획이 1개일 경우 자동 바인딩되고 2개 이상일 경우 매개변수 `plan_id`로 대상을 지정합니다. 활성 계획이 여러 개일 때 서버는 `next_action_hint` 안내에 명시적으로 plan_id 값을 포함해 응답하므로, 모델이 안내 힌트를 충실히 따르는 것만으로도 정확한 계획으로 라우팅됩니다. 승인 요청 역시 큐 방식으로 관리되므로 두 개 이상의 세션이 동시에 승인을 대기하면 승인 웹 UI 화면에 각 요청 카드가 병렬로 표시됩니다. 동시 활성 계획의 기본 상한은 `PLANNING_MCP_MAX_ACTIVE_PLANS=5`로 제어됩니다.
>
> 아래 내용은 **v1.7.0 이전** 단일 슬롯 아키텍처 기준의 배경 설명이며, 현재는 동일한 `goal` 문자열을 지닌 재계획 시나리오에 동일 원칙이 적용됩니다.

**(1.7.0 이전) 이 서버의 활성 계획 슬롯은 하나였습니다.** 동일한 state 디렉터리를 참조하는 모든 대화창과 워크스페이스가 하나의 계획 슬롯을 공유했습니다. 이는 단일 운영자가 한 번에 하나의 계획을 검토하고 승인한다는 HITL(Human-in-the-loop) 철학의 설계적 귀결이었습니다 (Phase 2 아키텍처 §9에서 복잡한 멀티 테넌시를 의도적으로 배제).

두 세션이 단일 슬롯에서 교차 실행될 때의 실제 동작 (실험 검증 완료):

| 기존 활성 계획의 상태 | 다른 세션에서 새 계획 생성을 시도할 경우 |
|---|---|
| `COMPLETED` 또는 `CANCELLED` | 새로운 `plan_id`가 발급되며 충돌 없이 깨끗하게 새 계획 시작 |
| `APPROVED` 또는 `IN_EXECUTION` | **신규 계획 생성이 엄격히 거부**되며 기존 진행 중인 계획으로 리다이렉트됨. 즉, 승인 완료된 계획은 타 세션에 의해 가로채질 수 없음 |
| `DRAFTING` 또는 `AWAITING_APPROVAL` | **기존 초안이 새 초안으로 대체됨.** 이전 작업 목록은 `superseded_tasks` 필드에 안전하게 보존되며, 감사 로그에 `goal_replaced` 이벤트가 기록되고, 응답의 `input_notes` 필드를 통해 모델에게 대체 사실이 경고됨 |

즉, 상태가 변경될 위험 구간은 "미결 상태의 작성 중 초안이 남아 있을 때"뿐이며, 이 경우에도 데이터 유실 없이 보존 이력이 남지만 **먼저 계획을 작성하던 세션의 맥락이 대체될 수 있습니다.**

**동시 요청 발생 시의 안전장치 (v1.6.0 검증 및 개선):** 서로 다른 서버 프로세스가 동일한 state 디렉터리에서 거의 동시에 계획을 수립할 경우, v1.5.0 이전에는 동일한 `plan_id` 발급으로 인한 파일 덮어쓰기 유실 위험이 있었습니다. v1.6.0부터는 운영체제 수준의 파일 잠금(FileLock) 메커니즘을 적용하여 모든 파일 쓰기를 완벽히 직렬화했습니다. 이에 따라 데이터 유실 대신 상기 표의 "초안 대체" 절차를 안전하게 수행하며 `goal_replaced` 감사 로그와 `superseded_tasks` 히스토리를 보존합니다. 또한 `plan_state.json` 파일 쓰기는 원자적 쓰기(Atomic Write)로 처리되어 어떠한 비정상 종료 상황에서도 파일이 손상되지 않습니다.

아울러 특정 세션의 승인 대기 상태가 **다른 세션의 독립적인 도구 호출을 블로킹하지 않습니다.** (과거 단일 락 시절 타 세션 호출이 최대 52초간 지연되던 문제를 해결함).

**미결 승인을 방치한 채 세션을 전환하는 경우의 방어 가드 (v1.2.0 도입):** 세션 1이 계획 A를 제시하고 승인을 대기하는 도중 세션 2가 새로운 계획 B로 초안을 대체한 경우, 사용자가 세션 1로 복귀하여 누른 "승인" 결정이 자신이 확인하지 않은 계획 B에 잘못 적용되는 치명적인 위험이 있었습니다. v1.2.0부터 승인 판정은 **사용자가 화면을 통해 마지막으로 확인한 정확한 작업 목록 버전**에만 한정하여 효력을 가집니다. 작업 목록이 조금이라도 변경되면 기존 승인 요청은 즉시 무효화되며, 해당 상태에서 전달된 `APPROVED` 결정은 `APPROVAL_NOT_REQUESTED` 에러로 단호히 거부됩니다(감사 로그 `stale_approval_refused`). 모델은 갱신된 현재 계획을 사용자에게 다시 제시하도록 강제되므로 오승인 사고가 원천 차단됩니다.

### 다중 세션 환경 권장 운영 수칙

1. **AnythingLLM 내 에이전트 전용 워크스페이스는 단 1개만 운용**하는 구성을 기본으로 권장합니다 (Phase 3 배포 지침과 동일).
2. **대화를 종료할 때는 계획을 승인 대기 상태로 방치하지 마십시오.** 대화를 마칠 때에는 승인 또는 반려 결정을 완료하여 계획을 터미널(종료) 상태로 마감하는 것이 다음 대화를 깨끗하게 시작하는 최선의 방법입니다.

> **v1.7.0부터 승인 웹 UI는 state 디렉터리당 단일 포트/단일 페이지로 통합되었습니다.** 복수의 서버 프로세스가 구동되거나 이전의 잔여 프로세스가 남아 있더라도, 모든 승인 요청은 **동일한 단일 웹 페이지 URL**로 수렴되어 노출됩니다. 승인 상태가 `state/approval.json` 공유 파일을 통해 관리되고, 포트를 선점한 프로세스가 해당 데이터를 통합 서비스하기 때문입니다. 선점 프로세스가 종료되면 대기 중이던 다른 프로세스가 포트를 즉시 자동 인계하므로 브라우저 탭 연결이 끊김 없이 유지됩니다. 즉, **이전 잔여 프로세스로 인해 승인 요청을 놓치거나 대화가 중단되는 위험이 완전히 해소되었습니다.**

3. **복수의 독립 워크스페이스를 반드시 병행 운용해야 한다면, 워크스페이스별로 MCP 서버 등록을 분리하고 state 디렉터리를 서로 다르게 지정하십시오.** 상태 저장소 디렉터리가 분리되면 완전한 상호 독립 격리가 보장됩니다:

```json
{
  "mcpServers": {
    "planning-work": {
      "command": "D:/planning-mcp/runtime/python.exe",
      "args": ["-u", "D:/planning-mcp/server.py"],
      "env": {
        "PYTHONUTF8": "1",
        "PYTHONUNBUFFERED": "1",
        "PLANNING_MCP_STATE_DIR": "D:/planning-mcp/state/work"
      },
      "anythingLLMAware": true
    },
    "planning-research": {
      "command": "D:/planning-mcp/runtime/python.exe",
      "args": ["-u", "D:/planning-mcp/server.py"],
      "env": {
        "PYTHONUTF8": "1",
        "PYTHONUNBUFFERED": "1",
        "PLANNING_MCP_STATE_DIR": "D:/planning-mcp/state/research"
      },
      "anythingLLMAware": true
    }
  }
}
```

각 워크스페이스의 Agent Skills 설정 메뉴에서 **해당 워크스페이스 전용 MCP 서버 하나만 선택 활성화**하십시오. 동일한 기능의 도구가 중복 노출되면 경량 모델의 도구 선택 오류가 급증할 수 있습니다. 워크스페이스별 도구 개별 활성화 기능을 지원하지 않는 구버전 AnythingLLM 환경이라면 수칙 1(단일 워크스페이스 전용 운용)을 적용하십시오.
4. SSE 전송 모드 역시 원리는 동일합니다. 워크스페이스마다 서로 다른 네트워크 포트와 상태 디렉터리를 부여하여 다중 인스턴스를 기동함으로써 완전한 독립 격리 환경을 구축할 수 있습니다.

## 부록 — 폐쇄망 반입 핵심 절차 요약 (One-page Cheat Sheet)

**개인 PC (반입 패키지 준비)**
```bash
python -m unittest discover -s tests
python tests/smoke_stdio.py
python tools/make_package.py --with-python C:\dl\python-3.12.10-embed-amd64.zip
```
→ 생성된 `dist/*.zip` 파일을 반입 매체로 복사하고, **콘솔에 출력된 SHA-256 체크섬을 별도 경로로 기록**
(사내 PC에 적정 버전의 Python이 확실히 설치되어 있다면 `--with-python` 옵션 생략 가능)

**사내 폐쇄망 PC (설치 및 서비스 기동)**
```powershell
# 1. 파일 무결성 해시값 대조
Get-FileHash .\planning-mcp-*.zip -Algorithm SHA256

# 2. 지정 경로에 압축 해제 및 Windows 파일 차단 일괄 해제
Expand-Archive .\planning-mcp-*.zip -DestinationPath D:\
Get-ChildItem -Recurse D:\planning-mcp | Unblock-File

# 3. 동봉된 파이썬 인터프리터 압축 해제 및 런타임 초기화
Expand-Archive D:\planning-mcp\runtime\python-*-embed-*.zip -DestinationPath D:\planning-mcp\runtime
D:\planning-mcp\runtime\python.exe D:\planning-mcp\tools\setup_runtime.py

# 4. 전체 환경 무결성 및 단위/종단 테스트 검증 (최종 GO 확인)
D:\planning-mcp\runtime\python.exe D:\planning-mcp\tools\verify_install.py
```
→ 검증 결과 **GO** 확인 후 AnythingLLM MCP 서버 등록 → 영문 시스템 프롬프트 반영 → temperature 0.3 설정 → **A1 사전 계획 강제 테스트 수행**

**반입 전 필수 체크리스트 2가지**
1. 파이썬 인터프리터를 패키지에 안전하게 동봉했는가? (사내 PC 환경이 불확실할 경우 반드시 동봉)
2. 패키지의 SHA-256 체크섬을 아카이브 외부의 별도 안전한 경로에 명확히 기록해 두었는가? (동봉 시 python.org 공식 공표 체크섬도 함께 확인)
