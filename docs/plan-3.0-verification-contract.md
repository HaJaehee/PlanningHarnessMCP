## 0. 한 줄 요약

2.0까지의 하네스는 **모델이 언제 행동해도 되는지**를 통제합니다(계획 → 승인 → 실행 → 완료 확인).
2026년 하네스 연구의 다음 단계는 **모델이 "했다"고 말한 것을 확인하는 것**입니다. 3.0은 이를 두 가지로 구현합니다.

- **검증 계약**: 태스크마다 **완료 기준**(`done_when`)을 정해 사람이 계획과 함께 승인하고, 서버가 확인할 수 있는
  것(파일이 실제로 있는지)은 직접 확인하며, 완료 화면은 기준·증거·서버 확인 결과를 나란히 보여 줍니다.
- **국소 재계획**: 태스크가 실패하면 그 태스크(와 뒤의 미착수 태스크)만 다시 쓰고, 이미 끝난 태스크의 결과는 유지합니다.

## 2. 이 프로젝트의 빈틈 (2.0 기준)

[wiki 00](../wiki/00-why-a-harness.md)과 [wiki 06](../wiki/06-human-in-the-loop.md)이 스스로 적어 둔 경계입니다.

> do no real work but write a plausible new `result_log` — **not detectable.** The server never sees the work.
> … the server enforces structure, the human checks substance.

2.0의 DONE 검사(`handlers.missing_evidence_reason`)가 막는 것은 네 가지뿐이었습니다: 빈 문자열, "완료했습니다" 같은
빈 주장, 태스크 제목 반복, 너무 짧은 글. 약점은 네 가지였습니다.

1. **"끝"의 정의가 없었습니다.** 사람이 완료 화면에서 증거를 비교할 대상이 태스크 제목뿐이었습니다.
2. **서버가 볼 수 있는 것도 보지 않았습니다.** "D:\reports\q4.xlsx로 저장했습니다"는 `os.stat` 한 번으로 확인됩니다.
3. **사람의 주의가 고르게 흩어졌습니다.** 확인된 사실과 모델의 말이 같은 무게로 나열되었습니다.
4. **실패 하나가 끝난 작업을 지웠습니다.** 태스크가 실패하면 계획 전체를 다시 세워야 했고, 그 과정에서 이미 끝난
   태스크의 증거가 버려졌습니다(5개 중 3번이 실패하면 1·2번을 다시 수행).

3.0은 이 경계를 없애지 못합니다. 경계를 옮기고, 사람이 볼 곳을 줄입니다.

## 4. 검증 계약

### 4.1 원칙

1. **거절은 구조적으로 불가능한 주장에만 씁니다.** 나머지는 사람에게 보여 줍니다. 잘못된 거절은 약한 모델에게
   반복 호출을 만듭니다(D25).
2. **서버는 읽기만 합니다.** `os.stat`만 호출합니다. 파일을 열지 않고, 허용한 폴더 밖은 디스크를 건드리지 않습니다.
3. **생략하면 2.0과 같습니다.** 응답도, 승인 지문도, 채팅용 문구도 같습니다(테스트로 고정).
4. **새 필드의 가장 게으른 사용부터 막습니다**(D19).
5. **상태를 추가하지 않습니다.** `PlanStatus`·`TaskStatus`·`NextAction`은 그대로이고 오류 코드 `FILE_NOT_FOUND` 하나만 늘었습니다.

### 4.2 모델 쪽 스키마

`plan_and_think`의 선택 필드. `task_updates`·`alternatives`와 같은 `{task_id, …}` 모양입니다.

```json
"done_when": [{"task_id": 2, "check": "A table with one revenue total per quarter (4 rows) exists"}]
```

`update_task_progress`의 선택 필드. `PLANNING_MCP_ARTIFACT_ROOTS`가 설정된 서버에서만 광고합니다.

```json
"files": ["D:/reports/q4_pivot.xlsx"]
```

- 완료 기준은 태스크의 **결과**에 붙습니다. 2.0의 대안은 **방법**이므로, 사람이 B안을 골라도 기준은 그대로입니다.
- 태스크당 기준은 하나(첫 번째), 길이 상한 200자(`PLANNING_MCP_MAX_DONE_WHEN_CHARS`).
- 초안과 함께 온 기준은 `draft_done_when`으로 보관하고, 서버가 초안을 자동 제출하거나 정지 카드에서 승인될 때 같이 갑니다.
- 입력 보정: `"2: …"` 문자열, `{"2": "…"}` 객체, 별칭(`criterion`, `criteria`, `acceptance` 등). `files`는 줄바꿈·세미콜론으로만
  나눕니다(쉼표는 파일 이름에 들어갈 수 있습니다).
- **스키마 비용(측정값)**: 새 필드만 더하면 도구 정의가 3,903 → 4,239토큰(+336), 파일 확인을 켜면
  4,354(+451)가 됩니다(`bytes // 3` 추정, `docs/context-budget-analysis.md`의 방법). 처음 예상(+250~300)보다
  컸으므로, 같은 릴리스에서 도구 설명 전체를 요약했습니다(§4.7). 최종값은 **3,486토큰**(파일 확인을 켜면
  3,599)이며, 2.0보다 작습니다.

### 4.3 가장 게으른 사용 막기

| 게으른 사용 | 막는 방법 |
|---|---|
| 내용 없는 기준 ("작업이 완료된다", 제목 반복) | 계획 단계에서 버리고 note |
| 기준 문장을 그대로 증거로 제출 | DONE 거절(`MISSING_RESULT_LOG`) |
| 만들지 않은 파일을 `files`에 적음 | DONE 거절(`FILE_NOT_FOUND`) |
| 거절당한 뒤 `files`를 빼고 다시 DONE | 받되 감사 로그 `file_claim_withdrawn`, 완료 화면에 표시 |
| 예전부터 있던 파일을 내세워 기준 반복을 통과 | 이 태스크 중에 생성·변경된 파일만 증거를 대신할 수 있음 |
| 확인하기 쉬운 것만 기준으로 삼음 | 서버가 못 막음. 승인 화면에서 사람이 기준을 보고 고침 |

**기준 반복 검사.** 증거의 문자 바이그램 중 기준에 없는 것의 비율(새 내용 비율)을 봅니다. 구현 중에 예시를 20개로
늘려 다시 재고, 처음 제안한 0.5를 **0.3으로 낮췄습니다.** 0.5였다면 `Saved the summary to out/summary.md (5 lines, 412 bytes)`
(0.39) 같은 정당한 보고를 거절했을 것입니다.

| 증거 | 새 내용 비율 | 3.0의 처리 |
|---|---:|---|
| 기준과 같은 문장 / 시제만 바꿈 | 0.00 ~ 0.25 | 거절 (0.3 미만) |
| 기준에 "(5줄)", 크기, 건수를 덧붙임 | 0.33 ~ 0.47 | 통과. 0.5 미만은 완료 화면에 "거의 그대로 반복" 표시 |
| 실제 값·이름·경로를 적음 | 0.59 ~ 0.93 | 통과 |

직접 만든 예시로만 확인한 값입니다(`tests/test_verification.py`의 `TestTheRepeatCheck`). 모든 DONE의 점수를 감사
로그(`task_done.novelty`)에 남기므로 현장에서 보정할 수 있습니다. `PLANNING_MCP_EVIDENCE_NOVELTY`로 조정하고 0이면 끕니다.

### 4.4 승인 창 — 계획 단계

```
2. 엑셀 피벗으로 매출 집계                                        [의견]
   완료 기준  분기별 매출 합계 4행이 있는 표가 만들어진다            [수정]
3. 5줄 요약 작성                                    [기준 추가]   [의견]
```

- 사람이 기준을 **직접 추가하거나 고치고 그대로 승인**합니다. 태스크 문구가 바뀌지 않으므로 수정 요청 왕복이 없습니다.
- 버튼이 결과를 먼저 말합니다: `승인 · 완료 기준 1건 반영`, 선택과 함께면 `승인 · 변경 3건 반영`.
- 기준이 없는 태스크에는 작은 `[기준 추가]` 버튼만 보입니다(1.11에서 의견칸을 접은 것과 같은 이유).
- 적은 내용은 `localStorage`에 두어 새로고침·다른 탭에서도 유지됩니다(D22).
- 결정 페이로드의 `criteria: {"3": "…"}`를 `record_decision`이 검증합니다. 화면에 없던 태스크나 끝난 태스크가 있으면
  결정 전체를 기록하지 않습니다.
- **모델은 기준을 대신 정할 수 없습니다.** 중계 필드를 아예 두지 않았습니다(채팅 모드 포함).
- 사람이 덮어쓴 모델의 원래 기준은 이후 어떤 응답에도 나오지 않습니다.
- 수정 요청을 누르기 전에 적은 기준도 버리지 않습니다. 태스크별 수정이면 그 태스크에 반영하고, 계획 전체 재작성이면
  의견에 붙여 모델에게 전달합니다.
- `PLANNING_MCP_DONE_WHEN=off`는 **모델의 필드**만 끕니다. 사람은 여전히 화면에서 기준을 적을 수 있습니다.

### 4.5 실행 단계

- 태스크를 넘겨줄 때마다 `next_task.done_when`과 힌트 문장으로 기준을 다시 말합니다. 현재 태스크의 기준만 싣습니다.
- DONE 검사(`_finish_task`, 기존 검사 뒤): ① `files` 확인 → 없거나 비어 있으면 `FILE_NOT_FOUND` ② 기준 반복 검사.
- 파일 확인 규칙:
  - `PLANNING_MCP_ARTIFACT_ROOTS`(`;` 구분) 안만 봅니다. 기본값은 비어 있고, 비어 있으면 확인하지 않으며 `files`도 광고하지 않습니다.
  - 폴더 밖(`..`, 다른 드라이브, UNC, 폴더 밖을 가리키는 링크)은 "확인 범위 밖"으로만 기록합니다. 거절하지 않습니다.
  - 상태: 이 태스크 중 생성·변경됨 / 작업 전부터 있던 파일 / 폴더 / 빈 파일 / 없음 / 범위 밖 / 확인 지연.
  - `result_log`에 적힌 경로도 뽑아 확인하되, **있는 것으로 확인된 것만** 표시합니다("임시 파일을 지웠습니다"가 있을 수 있습니다).
  - 확인은 제한 시간(3초)이 있는 보조 스레드에서 합니다. 응답이 늦으면 "확인 지연"이며 거절하지 않습니다.
- 같은 거절이 반복되면 1.16 브레이커가 정지 카드를 띄웁니다.

### 4.6 승인 창 — 완료 단계

```
완료 확인 · plan_20261003_0001
3개 중 1개는 태스크 중에 만들거나 바꾼 파일을 서버가 확인했습니다. 나머지 2개는 에이전트의 보고가 근거입니다.

1. 집계                                                소요 2분 14초
   완료 기준  합계 4행 표가 생긴다
   → 표를 만들어 pivot.xlsx 로 저장
   ✔ pivot.xlsx · 14.2 KB · 이 태스크 중 생성/변경됨
3. 요약                                                소요 3초
   완료 기준  요약이 5줄이다
   → 요약이 5줄이다
   ⚠ 처음에 summary.md 을(를) 결과 파일로 적었다가 뺐습니다 (서버가 찾지 못함)
   ⚠ 증거가 완료 기준 문장을 거의 그대로 반복합니다
```

- 완료 요청을 낼 때 확인된 파일을 한 번 더 봅니다. 그 사이 없어졌으면 "보고 당시에는 있었으나 지금은 없음"으로 표시합니다.
- 서버 확인 결과(경로와 상태)는 완료 지문에 들어갑니다. 크기와 수정 시각은 넣지 않습니다. 사람이 보고서를 읽다가
  파일을 열어 저장해도 요청이 무효가 되지 않습니다.
- 소요 시간은 표시만 합니다. 임계값 경고는 현장 데이터 없이 정하지 않았습니다.

### 4.7 도구 설명과 에이전트 프롬프트 요약

도구 설명은 현장 결함이 생길 때마다 문장을 덧붙이며 자랐습니다. `update_task_progress`는 "한 번에 한 태스크"를
세 번, FAILED 규칙을 두 번 말했고, `get_current_plan`은 설명과 매개변수가 같은 내용을 통째로 반복했습니다.

요약 원칙은 세 가지입니다.

1. **규칙은 한 번만, 도구 설명에 둡니다.** 일부 클라이언트는 스키마를 전달하면서 매개변수 설명을 빼거나
   줄입니다(테스트 매트릭스 E16). 도구 설명은 항상 전달됩니다.
2. **매개변수 설명에는 값의 모양과 예시 하나만 둡니다.**
3. **객체 배열은 배열에 예시를 한 번 둡니다.** 전체 모양을 보여 주는 예시가 약한 모델이 따라 쓰는 대상이고,
   안쪽 필드에는 몇 단어만 남깁니다.

뺀 것은 반복뿐입니다. 예시, 열거값, 규칙은 하나도 빼지 않았고 `TestToolTextIsLean`이 규칙과 크기 상한을
고정합니다. 문구를 고정하던 기존 테스트도 모두 그대로 통과합니다.

| 추정 토큰 | standard | reasoning |
|---|---:|---:|
| 2.0.0 | 3,903 | 3,703 |
| 3.0.0 새 필드 추가 직후 | 4,239 | 4,066 |
| **3.0.0 요약 후** | **3,486** | **3,325** |
| 파일 확인을 켠 경우 | 3,599 | 3,438 |
| `done_when`·국소 재계획을 끈 경우 | 3,181 | 2,993 |

도구별로는 `update_task_progress` 1,010 → 767, `get_current_plan` 451 → 273, `plan_and_think` 2,168 → 1,899,
`request_user_approval` 610 → 547입니다.

**사내 모델에서 검증하지 않았습니다.** 긴 설명은 약한 모델에게 필요해서 길어진 것이고, 반복 자체가 약한 모델에게
도움이 되었을 수 있습니다. 배포 후 도구 호출 오류가 늘면 가장 많이 줄인 `UPDATE_TASK_PROGRESS_DESCRIPTION`부터
되돌려 보십시오. 이 요약으로 "새 기능을 끄면 도구 목록이 2.0과 바이트 단위로 같다"는 성질은 없어졌습니다
(끄면 3.0 문구가 광고되지 않는다는 것만 보장합니다).

**에이전트 프롬프트(`agents.md`)도 요약했습니다.** 대상 모델이 중형 LLM이어서 프롬프트가 길면 오히려 준수율이
떨어진다는 사용자 판단에 따른 것입니다. 46줄·3,862자 → 31줄·2,275자입니다.

- 남긴 것: 프롬프트만 말할 수 있는 것. 생애주기, `next_action`이 모델 자신의 계획보다 우선한다는 것, 두 출구
  (`ANSWER_USER`, `display_to_user`), 답변 형식. 선택 필드(`alternatives`, `done_when`, `files`)는 한 줄씩,
  "도구에 있으면"이라는 조건을 달아 남겼습니다.
- 뺀 것: 도구 설명이 이미 말하거나, 서버 힌트가 그 순간에 알려 주는 규칙. `LOOP_HALTED`, 다시 작업 규칙,
  `task_updates`, `next_task`의 `task_id`, 거부되는 문구 등입니다. 무엇이 어디로 옮겨졌는지는
  [phase3 문서](phase3-anythingllm-agent-prompt.md)의 표에 있습니다.
- `TestPromptHygiene`이 양쪽을 고정합니다: 프롬프트에 남아야 하는 문장, 그리고 빠진 규칙이 도구 설명이나
  힌트 어딘가에 여전히 있다는 것.
- 2.0 문구에 머물러 있던 한국어 Variant B도 같은 내용으로 다시 썼습니다.
- README에서는 프롬프트 사본을 뺐습니다. `agents.md`가 원본이므로 그 파일을 붙여 넣으라고만 안내합니다.
- 역시 사내 모델에서 검증하지 않았습니다. 표의 동작 중 하나가 나빠지면 프롬프트 전체가 아니라 그 한 줄만
  되돌리면 됩니다.

## 5. 국소 재계획

- 태스크가 `FAILED`가 되면 서버가 그 태스크를 수정 대상으로 올립니다(`pending_revision`의 `origin: "failure"`).
  1.10의 태스크별 수정과 같은 경로이므로 모델은 이미 아는 `task_updates`를 씁니다.
- 힌트가 보낼 인자를 그대로 줍니다: `task_updates=[{"task_id": 3, "title": "<another way to do this task>"}]`.
- 실패한 태스크는 **반드시** 다시 써야 하고(같은 문구로 재시도도 허용), 그 뒤의 미착수 태스크는 고칠 **수 있으며**,
  끝난 태스크는 건드릴 수 없습니다(보내면 무시하고 note).
- 고친 뒤에는 사람의 재승인을 받습니다. 화면에는 이전 문구와 실패 사유가 함께 보입니다.
- 승인되면 고친 태스크에서 이어서 실행합니다. `next_task.failure_note`와 힌트가 이전 실패를 다시 말합니다.
- 전체 `task_list`를 보내는 2.0 방식도 그대로 받습니다. 이때는 2.0처럼 끝난 작업의 증거를 버리며, note와 감사 로그
  (`repair_ignored`)에 남깁니다.
- `PLANNING_MCP_LOCAL_REPAIR=false`이면 2.0 동작으로 돌아갑니다.
- 한계: 1:1 교체만 됩니다. 태스크 추가·삭제·순서 변경은 전체 재작성으로 합니다(안정 식별자가 필요한 작업으로, 여전히 미구현).

- 버전 옆의 작은 `i` 아이콘을 누르면 Author / Email / Version 대화상자가 열립니다. 값은
  `planning/config.py`의 `SERVER_AUTHOR`, `SERVER_AUTHOR_EMAIL`, `SERVER_VERSION`입니다.
- 결정 버튼을 누를 때 페이지의 모든 버튼을 비활성화하던 코드를 `#root` 안의 버튼만 비활성화하도록 고쳤습니다.
  그대로였다면 첫 결정 이후 아이콘이 영영 눌리지 않았을 것입니다.
- 브라우저로 확인했습니다: 세 화면의 버전 표시, 버전 불일치 안내, 대화상자 내용, 닫기 버튼과 Esc, 결정 후에도
  아이콘 동작, 콘솔 오류 없음.

### 활성 계획 한도에서의 LRU 정리

- 활성 계획 수가 `PLANNING_MCP_MAX_ACTIVE_PLANS`(20)에 도달한 상태에서 새 계획이 오면, 가장 오래 쓰이지 않은
  미완료 계획을 삭제해 자리를 만듭니다. `PLANNING_MCP_EVICT_LRU`(기본 `true`)로 켜고 끕니다. 끄면 이전처럼
  새 계획을 거절합니다.
- "쓰임"의 기준은 계획의 마지막 갱신 시각(`updated_at`)입니다. 승인을 기다리는 에이전트는 45초마다, 실행 중인
  에이전트는 태스크마다 계획을 갱신하므로, `PLANNING_MCP_EVICT_MIN_IDLE`(기본 300초) 안에 갱신된 계획은 사용 중으로
  보고 삭제하지 않습니다. 모든 계획이 사용 중이면 새 계획은 이전처럼 거절됩니다.
- 이 하한은 폭주 방지 장치이기도 합니다. 계획을 계속 새로 여는 모델은 자신이 방금 만든 계획이 자리를 다 채우는
  순간부터 거절되므로, 삭제는 많아야 한도 수만큼만 일어납니다.
- 조용히 사라지는 것은 없습니다. 삭제된 계획의 태스크와 증거는 감사 로그(`plan_evicted`)에 남고, 승인 페이지의
  요청은 내려가며, 상태 파일이 그 id를 기억합니다(최근 50건).
- 삭제된 계획의 대화가 돌아오면 어느 도구를 부르든 `PLAN_EVICTED` → `ANSWER_USER`를 받습니다. "다른 계획 중
  하나를 쓰라"며 다른 대화의 계획 목록을 보여 주는 일은 없습니다.
- **테스트가 찾은 결함(D29)**: 계획 id가 "오늘 계획 수 + 1"로 정해져, 삭제된 계획의 id를 그 자리를 차지한 새
  계획이 그대로 받았습니다. 돌아온 대화가 남의 새 계획으로 연결될 뻔했습니다. id를 "그날 발급한 최댓값 + 1"로
  바꿔 어떤 삭제 뒤에도 재사용되지 않게 했습니다.

## 10. 남은 일
