> **상태: 계획만 있음, 미구현.** 1.16.0(계획 단계 폭주 차단) 구현이 끝난 뒤 사용자와 다시

> 프로토콜이 바뀌므로 메이저).

---

## 1. 요구사항 (사용자 확정)

- 태스크 **제안은 모델**이 하고, **선택은 사용자가 승인 창에서** 합니다.
- Claude·Gemini처럼 선택지를 보여주고 그중 하나에 `권장` 표시를 붙입니다.
- 범위는 **2b: 서로 배타적인 대안 중 하나를 고르는 선택**입니다.
  (예: 2번 태스크 — "A안: 엑셀 피벗으로 집계 (권장)" / "B안: CSV로 내보낸 뒤 스크립트로 집계")
- 태스크를 빼는 다중 선택(2a)은 요청 범위가 아닙니다.

## 2. 1.16과의 연결 — 왜 이 기능이 폭주 대책이기도 한가

thinking 모델의 "wait, let me reconsider"는 대개 **두 방법 사이에서 오락가락**하는 데서 나옵니다.
1.16은 "검증은 사람의 일"이라는 출구를 주었고, 2.0은 그 망설임을 **사람이 고르는 선택지로**
바꾸는 통로를 줍니다. 그래서 2.0에서 reasoning 프로필 설명에 다음을 추가합니다:

> If you are torn between two ways of doing a task, do not reconsider. Put the one you prefer in
> task_list and the other in alternatives. The user picks.

---

## 3. 모델 쪽 (스키마)

- `task_list`는 **모델의 권장 계획**으로 그대로 둡니다 (문자열 배열).
- 새 파라미터 `alternatives`: 특정 태스크를 하는 다른 방법.
  모양은 이미 쓰고 있는 `task_updates`와 같게 합니다. 약한 모델이 새 모양을 익힐 필요가 없습니다.
  ```json
  "alternatives": [
    {"task_id": 2, "title": "CSV로 내보낸 뒤 스크립트로 집계", "reason": "빠르지만 서식이 사라짐"}
  ]
  ```
  `task_id`는 같은 호출의 `task_list` 안 번호(첫 태스크 = 1)입니다.
- **권장안은 항상 `task_list` 쪽입니다.** 몇 번이 권장인지 따로 적지 않으므로 틀릴 여지가 없습니다
  (Claude AskUserQuestion의 "권장은 첫 번째" 관례와 같은 발상).
- 생략하면 1.16과 완전히 같게 동작합니다 (하위 호환).
- 제한: 태스크당 대안 최대 3개(선택지 2–4개), 플랜당 선택 지점 최대 3개. 넘는 것은 잘라내고
  `input_notes`로 알립니다. 1.11에서 의견칸을 접은 것과 같은 이유 — 선택지가 많으면 계획이 설문지가 됩니다.
- 입력 보정(leniency): `"2: CSV로…"` 문자열, `option`/`text`/`alternative` 별칭을 받아줍니다.
  없는 번호, 권장안과 같은 문구, 빈 문자열은 지우고 note를 남깁니다.
- `alternatives`는 확정 호출(`need_more_thinking=false`)에서만 의미가 있습니다. 1.16의 초안 보관
  (`draft_tasks`)과 함께 초안 대안도 보관할지 착수 시 결정합니다.

## 4. 승인 창

```
2. 집계 방식
   ◉ 엑셀 피벗으로 집계                                  [권장]
   ○ CSV로 내보낸 뒤 스크립트로 집계 — 빠르지만 서식 손실
   ○ 기타 (직접 입력)
```

- 기본 선택은 권장안입니다.
- 버튼이 결과를 먼저 말합니다: 바꾸지 않으면 `승인`, 바꾸면 `승인 · 2번 B안`.
- **기타**를 고르면 그 태스크의 의견칸이 열리고 버튼이 `수정 요청 · 2번만`으로 바뀝니다.
  기존 태스크별 수정 흐름(1.10)을 그대로 씁니다 → "사람이 승인한 것 = 실행되는 것" 불변식 유지.
- 선택 상태는 의견 초안처럼 `localStorage`에 보관합니다 (D22: 카드 재렌더링이 선택을 지우지 않게,
  두 탭이 같은 선택을 보이게). 키 예: `planning-mcp:choice:<request_id>:<task_id>`.

## 5. 서버 쪽

- `Task`에 `options`(0번 = 권장 = 원래 title, 1.. = 대안 + reason)와 `chosen`(인덱스)을 둡니다.
- 결정 페이로드에 `choices: {"2": 1}` (task_id → 옵션 인덱스). `record_decision`에서 검증하고,
  범위를 벗어나면 기록하지 않고 페이지에 오류를 띄웁니다.
- 승인과 **같은 트랜잭션**에서 선택을 반영합니다: 태스크 title = 선택된 문구. audit `choices_applied`
  (전/후 문구).
- **승인 지문(fingerprint)**: 대안이 있는 플랜만 options를 지문에 포함합니다. 대안이 없는 플랜은
  지문이 1.16과 같아야 합니다 — 롤링 재시작 중 대기하던 요청이 무효화되지 않도록. 테스트로 고정.
- **D19 교훈 — 새 필드의 가장 게으른 사용부터 막기**: 승인 이후 모델에게 가는 응답에는 **고른 문구만**
  넣습니다. 고르지 않은 대안은 어떤 응답에도 다시 나오지 않게 합니다(보이면 그쪽을 해버릴 수 있음).
  힌트: "사용자가 2번을 B안으로 골랐다: '…'. 그 방법으로 하라."
- **모델이 대신 고르기 금지**: 승인 요청이 페이지에 떠 있는 동안 모델이 보낸 choices는 D20 가드로 거절.
  페이지가 없는 2단계(채팅) 모드에서만 `request_user_approval`의 선택적 `choices`를 받고,
  없으면 권장안으로 진행합니다.
- **완료 보고**: `2. (B안 선택) CSV로…` — 사람이 고른 방법대로 했는지 확인할 수 있게.
- **수정과의 관계**: 대안이 있는 태스크를 `task_updates`로 다시 쓰면 그 태스크의 대안은 버립니다
  (새 문구와 옛 대안이 맞지 않음). 전체 재작성은 새 `task_list` + 새 `alternatives`.
- **1.16 서킷 브레이커 카드의 `이 초안으로 승인`**: 대안이 있는 초안이면 권장안으로 승인할지, 선택 UI를
  그 카드에도 넣을지 착수 시 결정.
- **버전 혼재**: 대안 없는 옛 항목 → 기존 렌더링. 새 페이지가 옛 서버에 choices를 보내면 무시되고
  권장안으로 진행 (안전한 쪽으로 실패).

## 6. 테스트

- leniency 퍼징 (문자열 형식, 별칭, 잘못된 번호, 중복, 한도 초과).
- 대안 없는 플랜의 지문이 1.16과 같은지 고정.
- 잘못된 choices 거부, D20 경로(페이지 대기 중 모델 choices 거부).
- 승인 후 **모든** 모델 응답에서 고르지 않은 문구가 0회 나오는지 시나리오 전체 스캔.
- 완료 보고 표시.
- 페이지: 소켓 없는 템플릿 테스트(`TestCompletionPageTemplate` 방식) + 실제 브라우저로 라디오 기본값,
  기타 → 의견칸·버튼 문구 변화, 재렌더링 후 선택 유지, 두 탭 동기화를 눈으로 확인 (D18 교훈).
