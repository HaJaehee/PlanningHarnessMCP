## 1. 요구사항 (사용자 확정)

- 태스크 **제안은 모델**이 하고, **선택은 사용자가 승인 창에서** 합니다.
- Claude·Gemini처럼 선택지를 보여주고, 그중 하나에 `권장` 표시와 **이유**를 붙입니다.
- 범위는 **2b: 서로 배타적인 대안 중 하나를 고르는 선택**입니다.
  (예: 2번 태스크 — "A안: 엑셀 피벗으로 집계 (권장)" / "B안: CSV로 내보낸 뒤 스크립트로 집계")
- 태스크를 빼는 다중 선택(2a)은 요청 범위가 아닙니다.

## 2. 1.16과의 연결 — 이 기능이 폭주 대책이기도 한 이유

thinking 모델의 "wait, let me reconsider"는 대개 **두 방법 사이에서 오락가락**하는 데서 나옵니다.
1.16은 "검증은 사람의 일"이라는 출구를 주었고, 2.0은 그 망설임을 **사람이 고르는 선택지로**
바꾸는 통로를 줍니다. 그래서 reasoning 프로필의 `plan_and_think` 설명에 다음을 추가합니다.

> If you are torn between two ways of doing a task, do not reconsider. Put the one you prefer in
> task_list and the other in alternatives. The user picks.

standard 프로필에는 이 문장을 넣지 않습니다. 필드는 노출하지만 망설임을 대안으로 돌리라고 권하지는
않습니다(§3).

## 3. 모델 쪽 (스키마)

- `task_list`는 **모델의 권장 계획**으로 그대로 둡니다(문자열 배열).
- 새 파라미터 두 개는 모두 `task_updates`(1.10)와 같은 `{task_id, …}` 모양입니다. 약한 모델이
  새 형식을 익힐 필요가 없습니다.
  ```json
  "alternatives": [
    {"task_id": 2, "title": "CSV로 내보낸 뒤 스크립트로 집계", "reason": "빠르지만 서식이 사라짐"}
  ],
  "recommended_reasons": [
    {"task_id": 2, "reason": "보고서 서식이 그대로 유지됨"}
  ]
  ```
  - `task_id`는 같은 호출의 `task_list` 안 번호입니다(첫 태스크 = 1).
  - `recommended_reasons`는 **권장안(= `task_list` 쪽)을 고른 이유**입니다. 대안이 있는 태스크에만
    의미가 있습니다. 대안이 없는 태스크에 붙으면 고를 것이 없으므로 버리고 note를 남깁니다.
    (결정 §8-4. 같은 배열에 권장 이유를 섞거나 `task_list`와 나란한 배열로 받는 방식은, 약한 모델이
    순서를 어긋나게 쓰기 쉬워서 쓰지 않습니다.)
- **권장안은 항상 `task_list` 쪽입니다.** 몇 번이 권장인지 따로 적지 않으므로 틀릴 여지가 없습니다.
- 두 필드를 모두 생략하면 1.16과 완전히 같게 동작합니다(하위 호환).
- **노출 범위 (결정 §8-1)**: standard와 reasoning **두 프로필 모두** 노출합니다. 약한 모델이 오용하면
  `PLANNING_MCP_ALTERNATIVES=off`로 끕니다. off이면 두 필드를 광고하지 않고, 보내 와도 무시한 뒤
  note를 남깁니다.
- **한도**:
  - 태스크당 대안은 최대 3개(선택지 2~4개), 플랜당 선택 지점은 최대 3개입니다. 넘는 것은 잘라내고
    `input_notes`로 알립니다.
  - 환경 변수로 조정할 수 있게 합니다: `PLANNING_MCP_MAX_ALTERNATIVES`(3), `PLANNING_MCP_MAX_CHOICE_POINTS`(3).
  - 이유: 선택지가 많으면 계획이 설문지가 됩니다. 1.11에서 의견칸을 접은 것과 같은 이유입니다.
- **가장 게으른 사용 막기 (D19)**: 모델이 스스로 확인할 수 있는 사실까지 사람에게 떠넘기는 것("어느
  파일을 쓸까요, A 아니면 B?")이 이 필드를 가장 쉽게 오용하는 방법입니다.
  - 설명에 다음을 명시합니다: "only when the choice depends on the user's preference, not on facts
    you can check yourself".
  - 플랜당 3개 상한이 마지막 방어선입니다.
- **입력 보정(leniency)**:
  - `"2: CSV로…"` 같은 문자열, `option`/`text`/`alternative`/`why` 별칭을 받아줍니다.
  - `recommended_reasons`는 `{"2": "…"}` 형태도 받습니다.
  - 없는 번호, 권장안과 같은 문구, 빈 문자열은 지우고 note를 남깁니다.
- **초안 단계 (결정 §8-3)**: `need_more_thinking=true`와 함께 온 대안과 권장 이유도 초안의 일부로
  보관합니다(`draft_alternatives`). 사고 예산이 소진되어 서버가 초안을 자동 제출하면 대안도 함께
  올라갑니다. 모델이 망설인 지점이 그대로 사람의 선택지가 됩니다.
  - 대안은 `task_list`의 번호에 묶여 있습니다. 새 초안 `task_list`가 오면 기존 초안 대안을 버립니다.
  - `task_list` 없이 대안만 오면, 번호가 맞는 경우에 한해 현재 초안에 붙입니다.

## 4. 승인 창

```
2. 집계 방식
   ◉ 엑셀 피벗으로 집계                                  [권장]
     └ 보고서 서식이 그대로 유지됨
   ○ CSV로 내보낸 뒤 스크립트로 집계 — 빠르지만 서식 손실
   ○ 기타 (직접 입력)
```

- 기본 선택은 권장안입니다. 권장 이유가 있으면 권장안 아래에 표시합니다.
- 버튼이 결과를 먼저 말합니다. 바꾸지 않으면 `승인`, 바꾸면 `승인 · 2번 B안`입니다.
- **기타**를 고르면 그 태스크의 의견칸이 열리고 버튼이 `수정 요청 · 2번만`으로 바뀝니다. 기존
  태스크별 수정 흐름(1.10)을 그대로 쓰므로 "사람이 승인한 것 = 실행되는 것" 불변식이 유지됩니다.
- 선택 상태는 의견 초안처럼 `localStorage`에 보관합니다. 카드가 다시 그려져도 선택이 지워지지 않고,
  두 탭이 같은 선택을 보여 줍니다(D22). 키 예: `planning-mcp:choice:<request_id>:<task_id>`.
- **반복 감지(정지) 카드 (결정 §8-2)**: 초안에 대안이 있으면 정지 카드에도 같은 라디오 선택을
  보여 주고, `[이 초안으로 승인]`이 그 선택을 반영합니다.
  - 버튼 문구도 같은 규칙을 따릅니다. 예: `이 초안으로 승인 · 2번 B안`.
  - 정지 카드에는 **기타가 없습니다.** 다른 방향을 원하면 카드의 방향 입력칸과 `[의견 전달 후 계속]`을
    쓰면 됩니다(1.16 흐름 그대로).

## 5. 서버 쪽

- `Task`에 다음을 둡니다.
  - `options`: 0번 = 권장안(원래 title + 권장 이유), 1번부터 = 대안(+ reason)
  - `chosen`: 고른 옵션의 인덱스
- 결정 페이로드에 `choices: {"2": 1}`(task_id → 옵션 인덱스)를 추가합니다. `record_decision`에서
  검증하고, 범위를 벗어나면 기록하지 않고 페이지에 오류를 띄웁니다. PLAN 단계와 HALT 단계에서
  받습니다. 정지 카드의 APPROVED는 초안을 확정한 뒤 선택을 반영합니다.
- 선택은 승인과 **같은 트랜잭션**에서 반영합니다. 태스크 title을 선택된 문구로 바꾸고, audit에
  `choices_applied`(전/후 문구)를 남깁니다.
- **승인 지문(fingerprint)**: 대안이 있는 플랜만 options와 이유를 지문에 포함합니다. 대안이 없는
  플랜은 지문이 1.16과 같아야 합니다. 그래야 롤링 재시작 중 대기하던 요청이 무효가 되지 않습니다.
  테스트로 고정합니다.
- **D19 교훈**: 승인 이후 모델에게 가는 응답에는 **고른 문구와 그 이유만** 넣습니다.
  - 고르지 않은 대안은 어떤 응답에도 다시 나오지 않게 합니다. 보이면 모델이 그쪽을 해 버릴 수 있습니다.
  - 힌트 예: "사용자가 2번을 B안으로 골랐다: '…' (빠르지만 서식이 사라짐). 그 방법으로 하라."
- **모델이 대신 고르기 금지**: 승인 요청이 페이지에 떠 있는 동안 모델이 보낸 choices는 D20 가드로
  거절합니다. 페이지가 없는 2단계(채팅) 모드에서만 `request_user_approval`의 선택적 `choices`를 받고,
  없으면 권장안으로 진행합니다.
- **완료 보고**: `2. (B안 선택) CSV로…`처럼 표시해, 사람이 고른 방법대로 했는지 확인할 수 있게 합니다.
- **수정과의 관계**: 대안이 있는 태스크를 `task_updates`로 다시 쓰면 그 태스크의 대안은 버립니다.
  새 문구와 옛 대안이 맞지 않기 때문입니다. 전체 재작성은 새 `task_list` + 새 `alternatives`로 합니다.
- **버전 혼재**: 대안 없는 옛 항목은 기존 방식으로 렌더링합니다. 새 페이지가 옛 서버에 choices를 보내면
  무시되고 권장안으로 진행합니다(안전한 쪽으로 실패).
- **알려진 한계**: 대안은 태스크 하나를 다른 태스크 하나로 바꾸는 1:1 교체만 됩니다. 단계 수가 달라지는
  대안은 "기타" 또는 전체 재작성으로 다룹니다.

## 6. 테스트

- leniency 퍼징: 문자열 형식, 별칭, 잘못된 번호, 중복, 한도 초과, 대안 없는 태스크의 권장 이유.
- `PLANNING_MCP_ALTERNATIVES=off`: 광고하지 않고, 보내 와도 무시하고 note를 남기는지.
- 대안 없는 플랜의 지문이 1.16과 같은지 고정.
- 잘못된 choices 거부, D20 경로(페이지 대기 중 모델의 choices 거부).
- 승인 후 **모든** 모델 응답에서 고르지 않은 문구가 0회 나오는지 시나리오 전체를 검사.
- 초안 대안: 자동 제출에 함께 올라가는지, 새 `task_list`가 오면 버려지는지.
- 정지 카드: 대안이 있는 초안을 선택과 함께 승인하는 흐름(채팅·페이지·늦은 결정).
- 완료 보고 표시.
- 페이지:
  - 소켓 없는 템플릿 테스트
  - 실제 브라우저로 확인(D18 교훈): 라디오 기본값, 권장 이유 표시, 기타 → 의견칸과 버튼 문구 변화,
    정지 카드 선택, 다시 그려진 뒤 선택 유지, 두 탭 동기화

## 9. 구현·검증 결과

- 신규 모듈 `planning/choices.py`에서 대안을 검증합니다.
  - 모델이 보낸 대안: 태스크 목록 기준으로 검증
  - 페이지가 보낸 선택: 화면에 보였던 것만 허용(엄격)
  - 모델이 채팅에서 전달한 선택: 관대하게 검증하되, 잘못된 것은 권장안으로 되돌림
- 단위 테스트 519개(신규 76개)와 smoke 테스트 6개가 모두 통과했습니다. 기존 테스트는 기대값을 하나도 바꾸지 않았습니다.
- "고르지 않은 대안이 모델 응답에 나오지 않는다"는 보장 테스트는, 일부러 `Task.brief()`가 옵션을
  흘리게 바꾸면 실패하는 것까지 확인했습니다.
- 실제 승인 서버와 브라우저로 직접 확인했습니다.
  - 권장안이 기본 선택되고 배지와 이유가 표시됨
  - B를 고르면 승인 버튼이 `승인 · 2번 B안`으로 바뀜
  - 기타를 고르면 의견칸이 열리고 승인 버튼이 비활성화됨
  - 새로고침 후에도 선택이 유지됨
  - 클릭하면 대기 중이던 에이전트에게 고른 안과 그 이유만 전달됨
  - 완료 보고에 `B안 선택` / `권장안` 배지가 표시됨
  - 정지 카드에서 `이 초안으로 승인 · 3번 B안`이 동작함
- 같은 확인 과정에서 라디오 버튼의 접근성 이름이 "0"/"1"로 읽히는 문제를 발견해 `aria-label`을 추가했습니다.
- 남은 관찰 항목은 [wiki/11](../wiki/11-status-and-next-steps.md)의 "2.0.0 follow-up"에 있습니다.
  - 모델이 어떤 태스크에 대안을 제시하는지
  - 사용자가 권장안을 그대로 고르는 비율과 기타를 고르는 비율
